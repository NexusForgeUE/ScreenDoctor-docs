ScreenDoctor 1.0.0 est un plugin de test d'interface pour Unreal Engine 5.5-5.8, Windows 64-bit et UMG. UMG est le système d'Unreal qui crée les menus, boutons et écrans du jeu.

Vous débutez dans Unreal ? Suivez le petit exemple de ce guide. Une fixture est un adaptateur Blueprint qui ouvre un écran pour le test. Un scenario décrit les vérifications. Une suite regroupe les scénarios et leurs configurations.

Le plugin exécute les parcours que vous décrivez. Il ne découvre pas seul tous les menus et ne répare pas automatiquement votre interface. Les explications sont traduites ; les noms anglais des boutons et des nœuds Blueprint restent ceux de l'interface.

Installer et ouvrir le plugin

Choisir la version du moteur

Utilisez le paquet ScreenDoctor correspondant à Unreal Engine 5.5, 5.6, 5.7 ou 5.8. Le numéro apparaît sous votre installation dans Unreal Engine > Library du lanceur Epic Games.

Installation par Fab

  1. Fermez Unreal Editor. Dans la bibliothèque Fab du lanceur Epic Games, trouvez ScreenDoctor et installez-le pour le moteur de votre projet.
  2. Ouvrez le projet, puis Edit > Plugins. Recherchez ScreenDoctor, activez-le si nécessaire et redémarrez quand Unreal le demande.
  3. Ouvrez Tools > ScreenDoctor.

Installation d'un ZIP dans le projet

Le dossier du projet contient son fichier .uproject. Créez-y Plugins si nécessaire. Fermez Unreal et respectez cette arborescence :

MyGame/
  MyGame.uproject
  Content/
  Plugins/
    ScreenDoctor/
      ScreenDoctor.uplugin
      Resources/
      Source/

Ouvrez ensuite le projet, activez ScreenDoctor dans Edit > Plugins, redémarrez et ouvrez Tools > ScreenDoctor. Un paquet compilé contient aussi Binaries. Installez une seule copie, dans le moteur ou dans le projet. Les sources seules demandent les outils C++ Visual Studio et le Windows SDK compatibles, même pour un projet Blueprint. Choisissez le paquet compilé adapté si vous ne souhaitez pas compiler.

Créer un premier projet

Dans Unreal, choisissez Games > Blank > Blueprint, donnez un nom et cliquez sur Create. Retenez son dossier. Le Content Drawer, en bas de l'éditeur ou via Ctrl+Space, contient les assets : les éléments enregistrés du projet, comme les widgets et scénarios.

Une première vérification depuis un projet vide

Commencez par un écran, une langue et une résolution. L'exemple ne demande pas de C++. Les menus et nœuds Unreal sont indiqués en anglais ; utilisez leurs équivalents si votre éditeur emploie une autre langue.

  1. Dans Content Drawer > Content, faites un clic droit dans la zone des assets, choisissez New Folder et nommez le dossier UITests.
  2. Dans ce dossier, choisissez User Interface > Widget Blueprint, puis le parent User Widget si demandé. Nommez l'asset WBP_UIExample et ouvrez-le.
  3. Dans Designer, ajoutez un Canvas Panel depuis la Palette si aucun panneau racine n'existe. Ajoutez un contrôle Text, nommez-le TitleLabel dans Hierarchy et cochez Is Variable dans Details. Saisissez exactement Settings, une police de 32, la position Canvas X=100, Y=100 et la taille 600 x 100.
  4. Ajoutez au Canvas un Button nommé ContinueButton, avec Is Variable et Is Focusable activés. Position : X=100, Y=250 ; taille : 300 x 70. Son enfant Text contient Continue. Le titre et le bouton sont deux enfants du Canvas, pas l'un de l'autre.
  5. Cliquez sur Compile et Save.
  6. Suivez Connecter le widget et Décrire le scénario, puis reprenez ici.
  7. Dans Suites, choisissez Create suite et enregistrez DA_UIFirstSuite dans Content/UITests. Cliquez sur Edit suite properties et saisissez SuiteId = first_ui_suite. Dans une fenêtre compacte, revenez avec Back to controls. Dans Scenarios, sélectionnez DA_UIFirstScenario et cliquez sur Add scenario to suite.
  8. Dans Matrix, ajoutez 1280 x 720 avec Add resolution, puis supprimez la valeur initiale 1280 x 800 avec Remove si elle existe. Gardez 100%, en et Keyboard. Modifiez les deux derniers dans Edit cultures, input modes, exclusions and case limit, puis revenez aux contrôles si nécessaire. Laissez l'exécution packaged désactivée.
  9. Cliquez sur Preview selected cases and exclusions, sélectionnez l'unique cas et choisissez Save and run selected case. Le widget s'ouvre dans un processus séparé ; le bouton Play habituel n'est pas nécessaire.
  10. Dans Runs, choisissez le résultat terminé et son image. Vérifiez les cinq étapes et la capture menu_state. Elle est enregistrée sans comparaison de référence : ce premier essai ne prouve pas encore une correspondance visuelle.
Compilez et enregistrez le widget et la fixture avant le test. Run enregistre la suite et le scénario, mais ne compile pas tous les Blueprints de votre jeu.

Connecter le widget avec une fixture

Une fixture dérive de ScreenDoctorFixture. Elle crée l'écran, enregistre ses contrôles et indique quand il est prêt. Ne la placez pas dans le niveau et n'ajoutez pas la fixture elle-même au viewport.

Créer l'asset

  1. Ouvrez Tools > ScreenDoctor > Scenarios, cliquez sur Create scenario et enregistrez DA_UIFirstScenario dans Content/UITests. Gardez-le sélectionné.
  2. Cliquez sur Create Blueprint fixture, enregistrez BP_UIFixture au même endroit et ouvrez-le. Ce bouton l'assigne au scénario, mais crée un Blueprint vide, pas un menu fonctionnel.
  3. Dans My Blueprint, ajoutez la variable Menu de type WBP_UIExample Object Reference, puis Compile. Dans Functions, ouvrez Overrides et choisissez OpenScreen.

OpenScreen : créer et renvoyer l'écran

Ajoutez les nœuds par clic droit dans le graphe et reliez les broches blanches dans l'ordre. Create Widget utilise WBP_UIExample et Get Player comme Owning Player. Stockez Return Value dans Menu et dans RootWidget hérité. Activez Show Inherited Variables si nécessaire.

OpenScreen
  Create Widget (Class = WBP_UIExample, Owning Player = GetPlayer)
  -> Set Menu = Return Value
  -> Set RootWidget = Menu
  -> Add to Viewport (Target = Menu)
  -> GetRegistry -> Register Widget
       Locator: ScreenId = demo_menu, TestId = title, Context = ""
       Widget: Menu.TitleLabel
  -> GetRegistry -> Register Widget
       Locator: ScreenId = demo_menu, TestId = continue, Context = ""
       Widget: Menu.ContinueButton
  -> Return Menu

La cible Target de chaque Register Widget est Get Registry. Sur Locator, utilisez Make Screen Doctor Locator ou séparez la broche de structure et renseignez les trois champs distincts. Depuis Menu, récupérez l'objet TitleLabel ou ContinueButton pour la broche Widget. Renvoyez Menu dans la sortie de la fonction : c'est un objet widget, pas un booléen.

IsReady : attendre la disponibilité

Ajoutez l'override IsReady. Testez Menu avec Is Valid et un Branch : renvoyez false si invalide, sinon le résultat Is In Viewport de Menu. La fonction par défaut renvoie false ; sans votre implémentation, le délai expire.

CleanupCase : nettoyer

Ajoutez CleanupCase. Sur son entrée, faites un clic droit, choisissez Add Call to Parent Function et reliez l'appel, puis remettez Menu à None. Le parent retire RootWidget et vide le registre. Gardez les implémentations par défaut de CaptureInputState et RestoreInputState pour ce tutoriel à processus séparé. Compilez, enregistrez, puis passez au scénario.

Commencez à 100%. N'ajoutez d'autres tailles qu'après avoir relié le véritable changement d'échelle décrit dans Matrix.

Décrire les actions et vérifications

Dans Scenarios, sélectionnez DA_UIFirstScenario. Définissez ScenarioId = first_ui, Revision = 1 et vérifiez Fixture Class = BP_UIFixture.

  1. Ouvrez Edit fixture / steps. Développez Steps dans Details et ajoutez cinq éléments avec le + du tableau.
  2. Renseignez chaque élément dans l'ordre ci-dessous. Gardez Required activé et un délai positif : 5 secondes pour les quatre premières étapes.
  3. Dans Target, ScreenId et TestId sont des champs séparés ; laissez Context vide. Pour AnalyzeLayout, ajoutez un élément dans Layout > Targets et remplissez son locator.

La sélection dans la liste ouvre l'éditeur de l'étape. Chaque StepId doit être unique. Après un renommage, une suppression ou une duplication, sélectionnez de nouveau l'étape voulue. Conservez les identifiants et augmentez Revision lorsque vous changez volontairement le contrat du test.

Dans une fenêtre compacte, cliquez sur Back to controls pour quitter Details. Revenez à la première vérification afin de créer la suite et lancer un cas.

Identifier les widgets de façon stable

Un locator est une adresse composée de trois champs distincts :

ChampExempleRôle
ScreenIddemo_menuÉcran propriétaire du contrôle.
TestIdtitleContrôle dans cet écran.
Contextvide ou item:42Clé facultative pour un élément répété.

Enregistrez ces champs avec la véritable référence du widget lors de son ouverture. Ne saisissez pas toute la chaîne demo_menu/title dans TestId. Un texte traduit, des coordonnées ou l'indice d'un enfant ne sont pas des identifiants stables.

Pour commencer, saisissez les IDs directement. Refresh IDs et Assign locator to selected StepId lisent le registre d'une fixture ScreenDoctor active en PIE. Le Play ordinaire ne crée pas cette fixture et ne parcourt pas tous les widgets du jeu.

Deux widgets actifs avec le même locator produisent une ambiguïté : distinguez les IDs ou Context. Pour une liste virtualisée, votre adaptateur doit faire défiler et matérialiser l'entrée avant de l'enregistrer. Une entrée non créée ne démontre pas un défaut d'interface.

Résolutions, langues et taille du texte

Choisissez votre suite et ouvrez Matrix. Il n'existe pas de limite à trois résolutions : vous pouvez ajouter des formats 4K, ultralarges et portrait.

  1. Dans Viewport resolutions, saisissez Width et Height entiers de 1 à 16384, puis Add resolution. Remove supprime une ligne. Gardez au moins une taille valide.
  2. Dans Text scales, saisissez un pourcentage comme 125 et cliquez sur Add text scale. Supprimez les valeurs inutiles à côté des lignes. Le champ en pourcentage reçoit 125 ; TextScales stocke 1.25.
  3. Dans Edit cultures, input modes, exclusions and case limit, ajoutez par exemple en, de et fr ainsi que les modes d'entrée pris en charge. Le jeu doit déjà posséder les traductions et polices. Choisir une culture ne traduit pas le texte.
  4. Actualisez l'aperçu du plan : chaque scénario combine résolutions, langues, échelles et entrées, puis applique les exclusions. Un scénario, une entrée, deux résolutions, trois langues et deux échelles donnent 12 cas.
  5. Lancez un cas, puis Save and run suite. Au-delà de 20 cas sélectionnés, confirmez l'estimation. Case Limit limite le plan ; Exclusions omet les combinaisons indiquées.

Appliquer réellement l'échelle

La fixture doit implémenter ApplyTextScale ; le comportement par défaut accepte seulement 1.0. Ajoutez dans BP_UIFixture un float RequestedScale initialisé à 1.0. Dans cet override, si Scale > 0 et Scale <= 3, stockez Scale et renvoyez true ; sinon false. Cette plage appartient à l'adaptateur d'exemple. Le callback intervient avant OpenScreen : Menu n'existe pas encore.

Dans OpenScreen, après Set Menu et avant Add to Viewport, récupérez Menu.TitleLabel, puis Get Font. Reliez sa sortie à Break Slate Font Info et ajoutez Make Slate Font Info. Reliez les champs existants correspondants de Break à Make : Font Family (Font Object), Typeface (Typeface Font Name), matériau, contour et tous les autres paramètres disponibles. Pour Size uniquement, utilisez Round(32 * RequestedScale) au lieu de l'ancienne taille. Reliez le résultat de Make à Set Font sur Menu.TitleLabel, ainsi que les broches blanches d'exécution. Au besoin, tirez depuis la broche de police et cherchez Slate Font Info. Cet exemple agrandit le titre ; appliquez la même politique aux autres textes ou utilisez le réglage réel du jeu. Calculez toujours depuis la taille de base enregistrée, pas depuis une taille déjà agrandie.

Le viewport est la surface de dessin ; l'échelle de texte est un réglage du jeu. La mise à l'échelle Windows et le DPI physique du moniteur sont distincts. Matrix à 125% ne modifie pas le DPI Windows.

Lire les résultats dans Runs

  1. Dans Runs, sélectionnez une exécution terminée dans la liste du haut.
  2. Choisissez un scénario à gauche, puis un checkpoint et un mode d'entrée. Les colonnes indiquent résolution/échelle et les lignes les cultures.
  3. Filtrez avec All cases, Needs review, Passed ou More filters. Les exclusions peuvent entrer dans les totaux non filtrés ; ce ne sont pas des cas exécutés.
  4. Sélectionnez une cellule, cliquez sur Inspect case et utilisez Next finding pour lire le locator, Expected et Actual.
  5. Utilisez 100% pour les pixels réels et les barres de défilement ; Fit rétablit l'ajustement. Open original ouvre le fichier. Geometry snapshot est une mesure séparée, pas un calque garanti sur chaque pixel capturé.

Save and rerun case utilise le scénario enregistré correspondant. Une modification du contrat figé peut demander un nouveau plan. Export report copie un dossier partageable ; transmettez tout le dossier avec les images, pas uniquement le HTML.

Comprendre les remarques de mise en page

AnalyzeLayout inspecte les cibles enregistrées, ou tous les widgets enregistrés si Targets est vide. Il peut signaler du texte tronqué, des chevauchements et de petites métriques de police. Ajoutez un CaptureCheckpoint proche pour voir l'interface réelle.

Desired est la taille demandée par la mise en page du texte ; visible est la zone de découpe mesurée. Une description demandant 84 pixels de hauteur mais limitée à 46 peut être signalée même à 1920 x 1080. Un grand écran ne corrige pas une petite zone de texte.

Ce sont des candidats à examiner, pas une reconnaissance OCR de chaque caractère ni la preuve que toute superposition est erronée. Vérifiez les couches décoratives, le défilement et les troncatures volontaires.

  1. Ouvrez le cas exact et vérifiez langue, résolution, échelle et widget.
  2. Inspectez l'original : retour à la ligne, dimensions du conteneur, ancres, marges ou libellé plus court.
  3. Compilez, enregistrez et relancez les mêmes conditions et les autres configurations affectées.
  4. Pour une exception volontaire, ajoutez une suppression ciblée dans les paramètres du scénario avec RuleId, locator, dimensions et Reason compréhensible. Gardez sa justification traçable.

Un contenu dessiné sur mesure, du rich text ou une entrée non matérialisée peuvent nécessiter un adaptateur. Unsupported n'est pas une réussite.

Approuver une référence puis comparer

Une baseline est une image que vous approuvez volontairement comme référence correcte pour une configuration. Une simple capture ne constitue pas une assertion de régression visuelle.

  1. Activez Compare Baseline sur l'étape de capture, compilez/enregistrez le widget et la fixture, puis enregistrez le scénario. Dans Matrix, cliquez sur Preview selected cases and exclusions, choisissez le cas actualisé et Save and run selected case. Ne relancez pas l'ancien cas figé depuis Runs après changement du contrat. La première comparaison produit normalement NoBaseline.
  2. Examinez cette image dans Runs, puis Review baseline source. Autre chemin : Baselines, Refresh completed runs, sélection du cas original terminé et du checkpoint menu_state.
  3. Utilisez Review checkpoint si nécessaire. Inspectez Current avec Open original ou Comparison report. Vérifiez identité, langue, résolution et échelle.
  4. Saisissez le nom du réviseur, examinez les seuils et cliquez sur Approve reviewed image seulement pour une image correcte. Si la source a changé, examinez-la de nouveau.
  5. Relancez le même cas. Une référence compatible est maintenant disponible. En cas de différence, examinez Current, Baseline et Diff.

Exécuter et approuver sont deux actions séparées. Chaque langue, résolution, échelle, entrée et profil de rendu compatible demande sa référence. Une nouvelle version du moteur, Revision ou un nouveau profil de police/rendu peuvent demander une nouvelle validation.

Seuils et zones animées

Channel tolerance vaut 8 par défaut. Allowed changed fraction vaut 0.0005, soit 0.05% des pixels non masqués. N'augmentez pas le seuil pour cacher un défaut. Advanced source and masks accepte un JSON pour une zone volontairement changeante :

{"schemaVersion":1,"masks":[{"name":"clock","reason":"Animated clock","x":30,"y":20,"width":160,"height":40}]}

Les coordonnées sont des pixels de la capture. Donnez un nom et une raison à chaque masque ; masquer toute l'image est interdit. Conservez les références approuvées avec les assets examinés du projet.

Clavier, manette et fenêtres modales

Le premier exemple est statique. Pour interagir, rendez les vrais boutons focusables, définissez leur navigation et leurs événements OnClicked habituels. À l'ouverture, définissez le mode d'entrée du joueur et le focus initial.

OpérationUtilisation
FocusWidgetPlacer le focus initial ; cela ne prouve pas la navigation.
SendKeyTransmettre Down, Enter ou Escape au focus de l’interface contrôlée.
SendGamepadButtonTransmettre Gamepad_DPad_Down ou Gamepad_FaceButton_Bottom.
ClickWidgetCliquer sur un contrôle enregistré par le chemin d’entrée pris en charge.
AssertFocusedVérifier le contrôle qui possède le focus.
AssertNoModalInterroger l’observateur modal explicite de la fixture.

Pour tester la navigation, configurez explicitement Down/Up entre les boutons, envoyez une touche, puis vérifiez le focus. Ne remplacez pas cela par un appel direct à OnClicked. SendKey et SendGamepadButton utilisent le focus, pas Target.

Implémentez SupportsModalObservation = true et HasOpenModal avec le véritable booléen de fenêtre ouverte, mis à jour par son fonctionnement normal. OnlyInputModes sépare les étapes Keyboard et Gamepad.

PIE signifie Play In Editor. Une vérification dans le même processus demande CaptureInputState/RestoreInputState complets, appartenant au jeu. Sinon, utilisez un processus séparé sans inventer une restauration universelle. Le routage logiciel de manette ne demande pas de contrôleur physique ; le comportement matériel reste une autre vérification.

Automatiser et conserver les rapports

Exécutez les suites enregistrées avec le commandlet ScreenDoctor intégré à Unreal, par exemple dans une tâche de compilation. Ouvrez un terminal PowerShell et remplacez les chemins du projet et de l'éditeur. Utilisez la même version du moteur que votre projet. Aucun fichier de script supplémentaire n'est nécessaire.

$project = 'D:\Games\MyGame\MyGame.uproject'
$editor = 'D:\Epic\UE_5.8\Engine\Binaries\Win64\UnrealEditor-Cmd.exe'
& $editor $project -run=ScreenDoctor -Action=Run -Suite='/Game/UITests/DA_UIFirstSuite.DA_UIFirstSuite' -Mode=EditorStandalone -NullRHI -unattended

/Game/UITests/DA_UIFirstSuite.DA_UIFirstSuite est le chemin d'objet de la suite, pas un chemin de fichier Windows. Adaptez-le si vous renommez l'asset. Enregistrez la suite, le scénario, le widget et la fixture avant de lancer.

Code de sortieSignification
0Toutes les vérifications obligatoires ont réussi ; des remarques facultatives ou supprimées déclarées peuvent rester.
1Au moins une assertion a échoué, sans erreur prioritaire.
2Erreur de configuration, exécution ou stockage, y compris un plan vide.
3Remarque obligatoire non résolue, référence absente, vérification indisponible/ignorée, annulation ou exécution incomplète.

HTML sert à la lecture, JSON conserve les détails et JUnit s'intègre aux outils de compilation. L'historique se trouve normalement sous <Project>/Saved/ScreenDoctor, les références sous <Project>/ScreenDoctor/Baselines. Gardez tous les fichiers du rapport.

Cancel owned queue arrête la file du plugin en conservant les résultats disponibles. Pour nettoyer l'historique, exécutez l'action History ci-dessous avec votre dossier de rapports. Elle affiche seulement les dossiers éligibles. Ajoutez -Apply après avoir vérifié cet aperçu. -KeepLast=20 conserve les 20 dernières exécutions et les 20 dernières files terminées. Les références approuvées et les exécutions inachevées sont protégées. Séparez les références de l'historique ordinaire.

& $editor $project -run=ScreenDoctor -Action=History -OutputRoot='D:\Games\MyGame\Saved\ScreenDoctor' -KeepLast=20 -NullRHI -unattended

Dans ces exemples, -NullRHI concerne le commandlet de coordination. Run lance des processus distincts avec rendu GPU pour les captures ; une session graphique fonctionnelle reste nécessaire. Une capture du jeu avec NullRHI ne produit pas d'image d'interface. Le traitement et les rapports restent locaux, sans service d'analyse en ligne requis.

Vérifier un jeu compilé en Development

Un jeu packaged fonctionne hors de l'éditeur. Utilisez Development pour le lanceur de tests ScreenDoctor ; Shipping et Test excluent ce module.

  1. Dans Edit > Project Settings > Packaging, choisissez les cartes et cultures requises.
  2. Ajoutez le dossier des widgets, fixtures, scénarios et suites dans Additional Asset Directories to Cook s'ils ne sont pas déjà référencés. Le tutoriel utilise /Game/UITests. Le cook prépare les assets pour le jeu : leur présence dans l'éditeur ne suffit pas.
  3. Produisez le jeu Win64 Development avec les outils requis par votre installation Unreal.
  4. Dans Matrix, activez Use packaged Development executable, cliquez sur Browse... et choisissez le véritable .exe Development.
  5. Prévisualisez et lancez un cas, vérifiez viewport, culture et fichiers avant toute la suite.

Incluez les traductions et polices nécessaires. Le guide concerne UE 5.5-5.8 : gardez un paquet plugin/moteur cohérent pour l'exécution et les références.

Questions fréquentes

Puis-je dépasser trois résolutions ?

Oui. Ajoutez et supprimez vos formats dans Matrix. Les trois colonnes illustrées ne sont pas une limite.

125% change-t-il Windows ?

Non. Il demande l'échelle de texte réellement implémentée par le jeu ou la fixture. Le DPI du moniteur est distinct.

Tous les écrans sont-ils connectés après installation ?

Non. Connectez chaque écran ou famille avec une fixture, des IDs stables et des étapes. Commencez par le petit widget du tutoriel.

Needs review prouve-t-il un bug ?

Non. Examinez l'image et les mesures ; une troncature ou une superposition peuvent être intentionnelles.

Une nouvelle exécution approuve-t-elle l'image ?

Non. L'approbation exige un examen séparé et Approve reviewed image.

Le plugin inclut-il l'écran fantastique et les assets du tutoriel ?

L'écran fantastique appartient à un projet d'illustration séparé. Vous créez le petit exemple UMG avec ce guide ; installer le plugin ne crée pas ces assets de jeu.

Un compte d'analyse en ligne est-il nécessaire ?

Non. ScreenDoctor exécute les vérifications via Unreal et écrit les rapports localement.
