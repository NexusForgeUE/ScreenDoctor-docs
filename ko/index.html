플레이어가 문제를 발견하기 전에 게임 UI를 확인하세요.

같은 화면을 여러 해상도, 글자 크기, 언어로 열어 보세요. 이미지를 비교하고 잘린 문구를 확인한 뒤, 레이아웃을 수정하고 다시 검사할 수 있습니다.

1 화면 연결2 검사 정의3 조건 선택4 결과 확인

ScreenDoctor 1.0.0은 Unreal Engine 5.5-5.8, Windows 64-bit, UMG용 UI 테스트 플러그인입니다. UMG는 메뉴, 버튼 등 게임 화면을 만드는 Unreal의 시스템입니다.

Unreal이 처음인가요? 이 가이드의 작은 예제부터 따라 하세요. Fixture는 검사할 화면을 여는 Blueprint 어댑터입니다. Scenario는 검사 단계이고, suite는 시나리오와 실행 조건의 묶음입니다.

플러그인은 작성한 경로를 실행합니다. 모든 메뉴를 자동으로 탐색하거나 UI를 자동으로 수정하지는 않습니다. 설명은 번역했으며, 화면에서 찾을 수 있도록 버튼과 Blueprint 노드 이름은 영어로 유지합니다.

플러그인 설치 및 열기

엔진 버전 맞추기

Unreal Engine 5.5, 5.6, 5.7, 5.8 중 프로젝트와 맞는 ScreenDoctor 패키지를 사용하세요. Epic Games Launcher의 Unreal Engine > Library에서 설치된 엔진 버전을 확인할 수 있습니다.

Fab으로 설치

  1. Unreal Editor를 닫고 런처의 Fab 라이브러리에서 ScreenDoctor를 찾아 프로젝트의 엔진에 설치합니다.
  2. 프로젝트를 열고 Edit > Plugins에서 ScreenDoctor를 검색합니다. 필요하면 활성화하고 에디터를 다시 시작합니다.
  3. Tools > ScreenDoctor를 엽니다.

ZIP을 프로젝트에 설치

.uproject 파일이 들어 있는 곳이 프로젝트 폴더입니다. Plugins 폴더가 없으면 만들고, Unreal을 닫은 뒤 다음 구조로 압축을 풉니다.

MyGame/
  MyGame.uproject
  Content/
  Plugins/
    ScreenDoctor/
      ScreenDoctor.uplugin
      Resources/
      Source/

프로젝트를 열고 Edit > Plugins에서 활성화한 후 재시작하여 Tools > ScreenDoctor를 여세요. 컴파일된 패키지에는 Binaries도 있습니다. 엔진 또는 프로젝트 한 곳에만 설치하세요. 소스만 있는 패키지는 호환되는 Visual Studio C++ 도구와 Windows SDK가 필요하며 Blueprint 전용 프로젝트도 같습니다. 직접 빌드하지 않으려면 버전에 맞는 컴파일된 패키지를 사용하세요.

프로젝트가 아직 없다면

Unreal을 시작하고 Games > Blank > Blueprint를 선택해 이름을 입력한 뒤 Create를 누릅니다. 저장 위치를 기억하세요. 에디터 아래 Content Drawer 또는 Ctrl+Space에서 에셋을 관리합니다. 에셋은 위젯이나 검사 시나리오처럼 저장되는 프로젝트 요소입니다.

빈 프로젝트에서 첫 검사하기

화면 하나, 언어 하나, 해상도 하나로 시작하세요. 예제 작성에는 C++가 필요하지 않습니다. 메뉴와 노드는 영어 이름으로 안내하므로 다른 에디터 언어에서는 해당 항목을 찾으세요.

  1. Content Drawer > Content의 빈 곳을 오른쪽 클릭하고 New Folder로 UITests를 만듭니다.
  2. 그 안에서 User Interface > Widget Blueprint를 선택하고, 부모를 물으면 User Widget을 고릅니다. 이름을 WBP_UIExample로 정하고 엽니다.
  3. Designer에 루트가 없으면 Canvas Panel을 추가합니다. 그 안에 Text를 넣고 Hierarchy에서 TitleLabel로 이름을 바꾸며 Details의 Is Variable을 켭니다. 텍스트는 정확히 Settings, 글꼴 크기 32, Canvas 위치 X=100, Y=100, 크기 600 x 100으로 설정합니다.
  4. Canvas에 Button을 추가해 ContinueButton이라 하고 Is Variable과 Is Focusable을 켭니다. 위치 X=100, Y=250, 크기 300 x 70입니다. 버튼의 자식 Text에는 Continue를 넣습니다. 제목과 버튼은 Canvas의 별도 자식이어야 하며 서로 안에 넣지 않습니다.
  5. Compile과 Save를 누릅니다.
  6. 아래 위젯 연결과 시나리오 작성을 완료하고 돌아옵니다.
  7. Suites에서 Create suite를 눌러 Content/UITests에 DA_UIFirstSuite를 저장합니다. Edit suite properties에서 SuiteId = first_ui_suite를 설정하고 좁은 창에서는 Back to controls로 돌아옵니다. Scenarios에서 DA_UIFirstScenario를 선택해 Add scenario to suite를 누릅니다.
  8. Matrix의 Add resolution으로 1280 x 720을 추가하고 기본 1280 x 800이 있으면 Remove로 지웁니다. 100%, en, Keyboard만 남깁니다. 언어와 입력은 Edit cultures, input modes, exclusions and case limit에서 바꾸고 필요하면 제어 화면으로 돌아옵니다. packaged 실행은 아직 켜지 않습니다.
  9. Preview selected cases and exclusions에서 한 케이스를 고르고 Save and run selected case를 누릅니다. 별도 검사 프로세스에서 위젯이 열리므로 일반 Play 버튼은 필요하지 않습니다.
  10. Runs에서 완료된 결과와 이미지를 고릅니다. 다섯 단계와 menu_state를 확인하세요. 이 첫 캡처는 기준 비교 없이 저장하므로 시각적 일치까지 증명하지는 않습니다.
실행 전에 위젯과 fixture를 컴파일하고 저장하세요. Run은 suite와 scenario를 저장하지만 모든 게임 Blueprint를 자동으로 컴파일하고 저장하지 않습니다.

fixture로 위젯 연결하기

Fixture는 ScreenDoctorFixture를 상속하는 Blueprint입니다. 화면을 만들고 컨트롤을 등록하며 준비 상태를 알립니다. Fixture를 레벨에 배치하거나 fixture 자체를 위젯처럼 viewport에 넣지 마세요.

에셋 만들기

  1. Tools > ScreenDoctor > Scenarios에서 Create scenario를 눌러 Content/UITests에 DA_UIFirstScenario를 저장하고 선택 상태를 유지합니다.
  2. Create Blueprint fixture를 눌러 BP_UIFixture를 저장하고 엽니다. 시나리오에 할당되지만 생성되는 것은 빈 Blueprint이지 완성된 메뉴가 아닙니다.
  3. My Blueprint에 Menu 변수를 만들고 형식을 WBP_UIExample Object Reference로 지정한 뒤 컴파일합니다. Functions의 Overrides에서 OpenScreen을 고릅니다.

OpenScreen: 화면 생성 및 반환

그래프를 오른쪽 클릭해 노드를 추가하고 흰색 실행 핀을 순서대로 연결합니다. Create Widget의 Class는 WBP_UIExample, Owning Player는 fixture의 Get Player입니다. Return Value를 Menu와 상속된 RootWidget에 저장합니다. 보이지 않으면 Show Inherited Variables를 켭니다.

OpenScreen
  Create Widget (Class = WBP_UIExample, Owning Player = GetPlayer)
  -> Set Menu = Return Value
  -> Set RootWidget = Menu
  -> Add to Viewport (Target = Menu)
  -> GetRegistry -> Register Widget
       Locator: ScreenId = demo_menu, TestId = title, Context = ""
       Widget: Menu.TitleLabel
  -> GetRegistry -> Register Widget
       Locator: ScreenId = demo_menu, TestId = continue, Context = ""
       Widget: Menu.ContinueButton
  -> Return Menu

각 Register Widget의 Target에는 Get Registry를 연결합니다. Locator는 Make Screen Doctor Locator 또는 구조체 핀 분할로 세 필드를 따로 입력합니다. Widget에는 Menu에서 가져온 실제 TitleLabel이나 ContinueButton 참조를 연결합니다. 마지막에 함수 반환값으로 Menu를 연결하세요. 반환형은 불리언이 아니라 위젯 객체입니다.

IsReady: 준비 상태 확인

IsReady를 재정의하고 Is Valid와 Branch로 Menu를 검사합니다. 유효하지 않으면 false, 유효하면 Menu의 Is In Viewport 결과를 반환합니다. 기본 구현은 false이므로 그대로 두면 준비 시간 초과가 발생합니다.

CleanupCase: 상태 정리

CleanupCase를 추가하고 시작 노드를 오른쪽 클릭해 Add Call to Parent Function을 연결한 다음 Menu를 None으로 비웁니다. 부모가 RootWidget을 제거하고 등록을 초기화합니다. 별도 프로세스 예제에서는 CaptureInputState와 RestoreInputState를 기본값으로 둡니다. Compile, Save 후 시나리오로 진행합니다.

먼저 100%를 사용하세요. 다른 글자 크기는 Matrix의 실제 확대 처리를 연결한 다음 추가합니다.

동작과 검사 단계 작성

Scenarios에서 DA_UIFirstScenario를 고르고 ScenarioId = first_ui, Revision = 1, Fixture Class = BP_UIFixture를 설정합니다.

  1. Edit fixture / steps를 열고 Details에서 Steps 배열을 펼친 뒤 +로 요소 다섯 개를 만듭니다.
  2. 아래 표 순서대로 입력합니다. Required는 켜 두고 양수 제한 시간을 사용합니다. 처음 네 단계는 5초로 설정할 수 있습니다.
  3. 대상이 있는 단계는 Target.ScreenId와 Target.TestId를 별도로 입력하고 Context는 비웁니다. AnalyzeLayout은 Layout > Targets에 한 요소를 추가합니다.
StepId동작설정할 필드
wait.titleWaitForWidgetTarget.ScreenId = demo_menu
Target.TestId = title

Target.TestId = title

ExpectedText는 위젯의 Settings와 정확히 같아야 합니다. 캡처의 Compare Baseline은 끄고, 나중에 기준 이미지를 승인할 때 켭니다.

목록에서 단계를 선택하면 해당 편집기가 열립니다. StepId는 중복될 수 없습니다. 이름 변경, 삭제, 복제 후에는 올바른 단계를 다시 고르세요. 같은 용도의 ID는 유지하고 검사 약속을 의도적으로 바꿀 때 Revision을 높입니다.

좁은 창에서는 Back to controls로 Details에서 돌아옵니다. 첫 검사로 돌아가 suite를 만들고 한 케이스부터 실행합니다.

안정적인 ID로 위젯 찾기

Locator는 별도의 필드 세 개로 이루어집니다.

필드예의미
ScreenIddemo_menu컨트롤이 속한 화면.
TestIdtitle화면 안의 컨트롤.
Context비움 또는 item:42반복 목록 항목의 선택적 식별자.

화면을 열 때 실제 위젯 참조와 함께 등록하세요. demo_menu/title 전체를 TestId에 넣지 마세요. 번역된 문구, 좌표, 자식 순서는 안정적인 ID가 아닙니다.

처음에는 ID를 직접 입력합니다. Refresh IDs와 Assign locator to selected StepId는 PIE의 활성 ScreenDoctor fixture 등록을 읽습니다. 일반 Play는 fixture를 만들거나 게임의 모든 위젯을 검색하지 않습니다.

서로 다른 살아 있는 위젯이 같은 locator를 쓰면 모호해집니다. ID나 Context를 구분하세요. 가상화 목록에서는 어댑터가 항목까지 스크롤해 위젯을 생성한 후 등록해야 합니다. 아직 생성되지 않은 항목만으로 UI 오류라고 할 수 없습니다.

해상도, 언어, 글자 크기 선택

Suite를 고르고 Matrix를 엽니다. 4K, 울트라와이드, 세로 화면 등 직접 크기를 추가할 수 있으며 세 해상도로 제한되지 않습니다.

  1. Viewport resolutions에 1부터 16384까지의 정수 Width와 Height를 입력하고 Add resolution을 누릅니다. Remove는 해당 행을 지웁니다. 유효한 크기를 하나 이상 남기세요.
  2. Text scales에 125 같은 백분율을 넣고 Add text scale을 누릅니다. 필요 없는 행은 삭제합니다. 백분율 필드는 125, 내부 TextScales 값은 1.25입니다.
  3. Edit cultures, input modes, exclusions and case limit에서 en, de, fr 같은 언어와 지원하는 입력 모드를 추가합니다. 번역과 글꼴은 게임에 이미 있어야 하며 문화권 선택이 번역을 만들지는 않습니다.
  4. 계획을 갱신합니다. 각 시나리오와 모든 해상도, 언어, 배율, 입력을 조합한 뒤 제외 조건을 적용합니다. 시나리오 하나, 입력 하나, 해상도 둘, 언어 셋, 배율 둘이면 12케이스입니다.
  5. 한 케이스를 실행한 후 Save and run suite를 사용합니다. 선택이 20개를 넘으면 예상량 확인이 필요합니다. Case Limit은 계획 상한이며 Exclusions는 의도적인 조합 제외입니다.

실제 글자에 배율 적용하기

Fixture가 ApplyTextScale을 구현해야 하며 기본은 1.0만 허용합니다. BP_UIFixture에 float RequestedScale을 만들고 기본값을 1.0으로 둡니다. Override에서 Scale > 0 그리고 Scale <= 3이면 값을 저장하고 true, 아니면 false를 반환합니다. 이 범위는 예제 어댑터의 선택입니다. 호출은 OpenScreen 이전이므로 Menu는 아직 없습니다.

OpenScreen에서 Set Menu 뒤, Add to Viewport 앞에 Menu.TitleLabel의 Get Font를 가져옵니다. 출력을 Break Slate Font Info에 연결하고 Make Slate Font Info를 추가합니다. Break의 기존 필드를 Make의 해당 입력에 연결합니다. Font Family(Font Object), Typeface(Typeface Font Name), 머티리얼, 외곽선과 나머지 노출된 설정을 유지합니다. Size만 Round(32 * RequestedScale)로 바꿉니다. Make의 결과를 Menu.TitleLabel의 Set Font에 연결하고 흰색 실행 핀도 연결합니다. 노드가 보이지 않으면 폰트 핀에서 드래그하여 Slate Font Info를 검색합니다. 이 예제는 제목만 확대합니다. 다른 텍스트에도 같은 정책을 적용하거나 실제 게임 설정을 호출하세요. 이미 확대한 크기가 아니라 저장된 기본 크기에서 계산해야 합니다.

Viewport는 그리기 영역이고 글자 배율은 게임 설정입니다. Windows 화면 배율과 모니터의 물리 DPI는 별개입니다. Matrix의 125%는 Windows DPI를 바꾸지 않습니다.

Runs에서 결과 읽기

  1. Runs 상단 목록에서 완료된 실행을 선택합니다.
  2. 왼쪽에서 시나리오를 고른 뒤 checkpoint와 입력 모드를 고릅니다. 열은 해상도/글자 배율, 행은 언어입니다.
  3. All cases, Needs review, Passed, More filters로 좁힙니다. 필터 없는 합계에는 계획에서 제외된 케이스가 포함될 수 있으나 실행된 케이스는 아닙니다.
  4. 셀을 선택해 Inspect case를 누르고 Next finding으로 locator, Expected, Actual을 확인합니다.
  5. 100%로 원래 픽셀을 보고 스크롤합니다. Fit은 맞춤 보기, Open original은 파일 열기입니다. Geometry snapshot은 별도 측정이며 캡처의 모든 픽셀에 정확히 맞는 오버레이를 보장하지 않습니다.

Error / Errored설정, 실행 또는 저장 오류입니다.이유와 프로세스 로그를 확인하세요.
Unsupported필요한 기능이 없습니다.어댑터를 구현하거나 지원 설정을 선택하세요.
Complete실행이 끝났다는 상태입니다.결과를 별도로 보세요. Passed라는 뜻이 아닙니다.

Save and rerun case는 저장된 일치 시나리오를 사용합니다. 고정된 검사 조건이 바뀌면 새 계획이 필요할 수 있습니다. Export report는 공유용 폴더를 복사합니다. HTML만이 아니라 이미지와 함께 전체 폴더를 전달하세요.

글자 잘림과 레이아웃 지적 이해하기

AnalyzeLayout은 선택한 등록 대상, Targets가 비어 있으면 등록된 모든 위젯을 확인합니다. 잘림, 겹침, 작은 글꼴 메트릭을 지적할 수 있습니다. 가까운 단계에 CaptureCheckpoint를 넣으세요.

Desired는 텍스트 레이아웃이 요구하는 크기, visible은 측정된 표시 영역입니다. 설명이 높이84픽셀을 요구하지만46만 받는다면 1920 x 1080에서도 지적됩니다. 큰 화면이 작은 텍스트 상자를 자동으로 늘리지는 않습니다.

이는 검토 후보이며 모든 글리프를 읽는 OCR도, 모든 겹침이 오류라는 판정도 아닙니다. 장식 레이어, 스크롤 영역, 의도적 생략을 확인하세요.

  1. 정확한 케이스와 대상을 열어 언어, 해상도, 배율을 확인합니다.
  2. 원본과 레이아웃에서 줄바꿈, 컨테이너, 앵커, 여백, 짧은 문구를 검토합니다.
  3. 컴파일하고 저장한 뒤 같은 조건과 영향을 받는 다른 조건을 다시 실행합니다.
  4. 의도한 상태라면 시나리오에 RuleId, locator, 적용 조건, 명확한 Reason으로 범위가 좁은 suppression을 추가합니다. 이유를 추적할 수 있게 남깁니다.

사용자 정의 그리기, 리치 텍스트, 미생성 목록 항목은 별도 어댑터가 필요할 수 있습니다. Unsupported는 통과가 아닙니다.

기준 이미지 승인 후 다시 비교하기

Baseline은 한 구성에서 올바르다고 직접 승인한 이미지입니다. 비교 없는 캡처는 시각적 회귀 검사를 수행한 것이 아닙니다.

  1. 캡처 단계의 Compare Baseline을 켜고 위젯과 fixture를 Compile/Save한 뒤 시나리오를 저장합니다. Matrix에서 Preview selected cases and exclusions를 갱신하고 새 케이스를 선택해 Save and run selected case를 누릅니다. 조건 변경 후 Runs의 이전 고정 케이스를 재실행하지 마세요. 첫 비교는 보통 NoBaseline입니다.
  2. Runs에서 해당 이미지를 확인하고 Review baseline source를 선택합니다. 또는 Baselines의 Refresh completed runs에서 완료된 원본 케이스와 menu_state를 고릅니다.
  3. 필요하면 Review checkpoint를 누르고 Current를 Open original 또는 Comparison report로 확인합니다. 식별 정보, 언어, 해상도, 배율을 대조하세요.
  4. 검토자 이름과 허용치를 확인한 뒤 올바른 이미지에만 Approve reviewed image를 누릅니다. 원본이 바뀌면 다시 검토합니다.
  5. 같은 케이스를 재실행합니다. 차이가 있으면 Current, Baseline, Diff를 살펴봅니다.

실행과 승인은 별도입니다. 언어, 해상도, 배율, 입력, 호환 렌더링 프로필마다 맞는 기준이 필요합니다. 엔진, Revision, 글꼴/렌더링 프로필 변경은 재검토를 요구할 수 있습니다.

허용치와 움직이는 영역

기본 Channel tolerance는8, Allowed changed fraction은0.0005로 마스크 밖 픽셀의0.05%입니다. 오류를 숨기려고 높이지 마세요. Advanced source and masks에서 의도적으로 움직이는 영역의 JSON을 지정할 수 있습니다.

{"schemaVersion":1,"masks":[{"name":"clock","reason":"Animated clock","x":30,"y":20,"width":160,"height":40}]}

좌표는 캡처 픽셀 기준입니다. 각 마스크에는 이름과 이유가 필요하며 전체 이미지를 가릴 수 없습니다. 승인 이미지는 검토된 프로젝트 파일과 함께 관리하세요.

키보드, 게임패드, 모달 창 검사

첫 예제는 정적 화면입니다. 상호작용 검사를 위해 실제 버튼을 포커스 가능하게 하고 탐색과 정상 OnClicked를 구현합니다. 화면을 열 때 입력 모드와 시작 포커스를 설정하세요.

동작용도
FocusWidget시작 포커스 설정. 이것만으로 탐색을 검사하지는 않습니다.
SendKey소유한 포커스의 UI에 Down, Enter, Escape 전송.
SendGamepadButtonGamepad_DPad_Down 또는 Gamepad_FaceButton_Bottom 전송.
ClickWidget지원 입력 경로로 등록 컨트롤 클릭.
AssertFocused포커스를 가진 컨트롤 확인.
AssertNoModalfixture의 명시적 모달 관찰자 사용.

버튼 사이 Down/Up을 명시하고 키를 보낸 다음 포커스를 검증하세요. Fixture에서 OnClicked를 직접 호출해 대체하지 마세요. SendKey와 SendGamepadButton은 Target이 아니라 현재 포커스를 사용합니다.

SupportsModalObservation = true와 실제 창 열림 상태를 반환하는 HasOpenModal을 구현하세요. 정상 열기/닫기 흐름에서 상태를 갱신합니다. OnlyInputModes로 Keyboard와 Gamepad 단계를 분리합니다.

PIE는 Play In Editor입니다. 같은 프로세스에서는 게임이 소유한 완전한 CaptureInputState/RestoreInputState가 필요합니다. 없으면 별도 프로세스를 사용하세요. 소프트웨어 게임패드 경로는 물리 컨트롤러를 요구하지 않으며 장치별 동작은 별도 검사입니다.

자동 실행과 보고서 보관

PowerShell로 저장된 에셋을 실행하고 빌드 작업에 넣을 수 있습니다. 프로젝트 폴더에서 터미널을 열고 예제 경로를 자신의 경로로 바꾸세요. 엔진 설치라면 그 플러그인의 Scripts 폴더를 사용합니다.

$project = 'D:\Games\MyGame\MyGame.uproject'
$engine = 'D:\Epic\UE_5.8'
.\Plugins\ScreenDoctor\Scripts\Run-ScreenDoctorSuite.ps1   -ProjectFile $project -EngineRoot $engine   -SuiteAsset '/Game/UITests/DA_UIFirstSuite.DA_UIFirstSuite'   -Mode EditorStandalone

/Game/UITests/DA_UIFirstSuite.DA_UIFirstSuite는 suite 객체 경로이며 Windows 파일 경로가 아닙니다. 에셋 이름을 바꿨다면 수정하세요. 스크립트는 플러그인의 Scripts에 있습니다.

종료 코드의미
0선택한 모든 필수 검사 통과. 미리 선언한 선택적 또는 억제된 지적이 남을 수 있습니다.
1우선순위가 더 높은 오류 없이 하나 이상의 단언 실패.
2설정, 실행 또는 저장 오류. 빈 계획도 포함합니다.
3미해결 필수 검토, 기준 없음, 미지원/건너뜀, 취소 또는 미완료.

HTML은 열람용, JSON은 전체 정보, JUnit은 빌드 도구용입니다. 보통 기록은 <Project>/Saved/ScreenDoctor, 기준은 <Project>/ScreenDoctor/Baselines에 있습니다. 보고서 전체를 보관하세요.

Cancel owned queue는 플러그인 큐를 중지하고 현재 결과를 보존합니다. Clear-ScreenDoctorHistory.ps1은 삭제 대상을 먼저 보여 주고 -Apply를 사용해야 삭제합니다. 승인 기준을 일반 실행 기록처럼 지우지 마세요.

캡처에는 실제 GPU 렌더링 세션이 필요하며 NullRHI는 UI 이미지를 만들 수 없습니다. 검사와 보고서는 로컬에서 처리하고 온라인 분석 서비스는 필요하지 않습니다.

Development 패키지 게임 검사

패키지 게임은 에디터 밖에서 실행합니다. ScreenDoctor 실행 모듈이 필요하면 Development를 사용합니다. Shipping과 Test는 해당 모듈을 제외합니다.

  1. Edit > Project Settings > Packaging에서 필요한 맵과 언어를 고릅니다.
  2. 다른 참조가 없다면 fixture, widget, scenario, suite 폴더를 Additional Asset Directories to Cook에 추가합니다. 이 예제는 /Game/UITests입니다. Cook은 게임용 에셋을 준비하며, 에디터에 있다는 것만으로 패키지 포함을 보장하지 않습니다.
  3. 해당 Unreal 설치에 필요한 도구로 Win64 Development를 빌드합니다.
  4. Matrix에서 Use packaged Development executable을 켜고 Browse...로 실제 Development .exe를 고릅니다.
  5. 계획을 보고 한 케이스를 실행하여 viewport, 언어, 파일을 확인한 후 전체 suite를 실행합니다.

번역과 글꼴도 포함해야 합니다. 가이드는 UE 5.5-5.8을 대상으로 하며 실행과 기준 승인에 맞는 엔진/플러그인 버전을 사용합니다.

자주 묻는 질문

해상도를 세 개보다 많이 검사할 수 있나요?

네. Matrix에서 직접 추가하고 삭제합니다. 예시의 세 열은 제한이 아닙니다.

125%가 Windows 배율을 바꾸나요?

아니요. 게임이나 fixture가 구현한 글자 배율을 요청합니다. 모니터 DPI와는 별개입니다.

설치하면 모든 메뉴가 자동 연결되나요?

아니요. Fixture, 안정적인 ID, 단계로 화면이나 화면 묶음을 연결합니다. 작은 예제부터 시작하세요.

Needs review면 확정된 버그인가요?

아니요. 이미지와 측정값으로 판단하세요. 의도적 잘림이나 장식적 겹침일 수 있습니다.

재실행하면 이미지가 승인되나요?

아니요. 별도 검토와 Approve reviewed image가 필요합니다.

판타지 화면과 튜토리얼 에셋이 포함되나요?

판타지 화면은 별도 설명용 프로젝트입니다. 작은 UMG 예제는 이 가이드로 직접 만들며 설치만으로 생성되지 않습니다.

클라우드 분석 계정이 필요한가요?

아니요. ScreenDoctor는 Unreal에서 로컬로 실행하고 로컬 보고서를 작성합니다.
