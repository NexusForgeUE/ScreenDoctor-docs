开始第一次检查安装 ScreenDoctor
1 连接界面2 编写检查3 选择条件4 查看结果

ScreenDoctor 1.0.0 是面向 Unreal Engine 5.5-5.8、Windows 64-bit 和 UMG 的界面测试插件。UMG 是 Unreal 中创建菜单、按钮和游戏界面的系统。

第一次使用 Unreal？ 请从本指南的小示例开始。Fixture 是打开待测界面的蓝图适配器；scenario 描述检查步骤；suite 把场景和运行条件组合在一起。

插件执行你编写的操作路径，不会自动探索所有菜单，也不会自动修复界面。说明文字已翻译；按钮名称和蓝图节点保留英文，以便与编辑器对应。

安装并打开插件

选择匹配的引擎版本

请使用适用于 Unreal Engine 5.5、5.6、5.7 或 5.8 的 ScreenDoctor 安装包。Epic Games Launcher 的 Unreal Engine > Library 中会在引擎安装项下显示版本。

通过 Fab 安装

  1. 关闭 Unreal Editor。在启动器的 Fab 库中找到 ScreenDoctor，为项目使用的引擎安装插件。
  2. 打开项目，在 Edit > Plugins 中搜索 ScreenDoctor，必要时启用并重启编辑器。
  3. 选择 Tools > ScreenDoctor。

从 ZIP 安装到项目

项目文件夹就是包含 .uproject 文件的文件夹。必要时新建 Plugins，关闭 Unreal，并按以下层级解压：

MyGame/
  MyGame.uproject
  Content/
  Plugins/
    ScreenDoctor/
      ScreenDoctor.uplugin
      Resources/
      Source/

然后打开项目，在 Edit > Plugins 中启用 ScreenDoctor，重启并打开 Tools > ScreenDoctor。预编译包还包含 Binaries。只安装一份，可以装在引擎或项目中。源码包需要匹配的 Visual Studio C++ 工具和 Windows SDK，即使项目只使用蓝图也一样。不想自行编译时，请选择对应版本的预编译包。

还没有项目？

启动 Unreal，选择 Games > Blank > Blueprint，输入名称并点击 Create。记住保存目录。编辑器底部的 Content Drawer，或快捷键 Ctrl+Space，用于管理资源。资源是保存的项目对象，例如控件蓝图和测试场景。

从空项目开始第一次检查

先使用一个界面、一种语言和一种分辨率。创建本示例不需要 C++。以下使用英文菜单和节点名；如果编辑器语言不同，请查找对应项目。

  1. 在 Content Drawer > Content 中右键空白区域，选择 New Folder，创建 UITests 文件夹。
  2. 在其中选择 User Interface > Widget Blueprint；如果询问父类，选择 User Widget。命名为 WBP_UIExample 并双击打开。
  3. 在 Designer 中，如果没有根面板，从 Palette 添加 Canvas Panel。在其中添加 Text，在 Hierarchy 中命名为 TitleLabel，并在 Details 中勾选 Is Variable。文字必须为 Settings，字号 32，Canvas 位置 X=100, Y=100，大小 600 x 100。
  4. 向 Canvas 添加 Button，命名为 ContinueButton，启用 Is Variable 和 Is Focusable。位置为 X=100, Y=250，大小为 300 x 70。在按钮内添加显示 Continue 的 Text。标题和按钮必须是 Canvas 下的两个独立子项，不能互相包含。
  5. 点击 Compile 和 Save。
  6. 完成下方的连接控件和编写测试场景，再回到此处。
  7. 在 Suites 中点击 Create suite，将 DA_UIFirstSuite 保存到 Content/UITests。打开 Edit suite properties，设置 SuiteId = first_ui_suite。窄窗口中可点击 Back to controls 返回。然后在 Scenarios 选中 DA_UIFirstScenario，点击 Add scenario to suite。
  8. 在 Matrix 中通过 Add resolution 添加 1280 x 720，如果存在默认的 1280 x 800，用 Remove 删除。只保留 100%、en 和 Keyboard。通过 Edit cultures, input modes, exclusions and case limit 修改语言与输入方式，必要时返回控制界面。不要启用 packaged 运行。
  9. 点击 Preview selected cases and exclusions，选择唯一的测试用例，再点击 Save and run selected case。插件会在单独的测试进程中打开控件，无需点击普通 Play。
  10. 进入 Runs，选择完成的结果与图像。检查五个步骤和 menu_state 截图。第一次只保存图像，不与基准比较，因此尚不能证明视觉一致。
运行前必须编译并保存控件和 fixture。Run 会保存 suite 和 scenario，但不会自动编译并保存游戏中的所有蓝图。

用 fixture 连接控件

Fixture 是继承 ScreenDoctorFixture 的蓝图，负责创建界面、注册控件并报告就绪状态。不要把 fixture 放进关卡，也不要把 fixture 本身当作界面加入 viewport。

创建资源

  1. 打开 Tools > ScreenDoctor > Scenarios，点击 Create scenario，将 DA_UIFirstScenario 保存到 Content/UITests，并保持选中。
  2. 点击 Create Blueprint fixture，保存并打开 BP_UIFixture。该按钮会将它分配给场景，但只创建空蓝图，不会生成可运行菜单。
  3. 在 My Blueprint 中创建 Menu 变量，类型设为 WBP_UIExample Object Reference，然后编译。在 Functions 的 Overrides 菜单中选择 OpenScreen。

OpenScreen：创建并返回界面

在图表中右键添加节点，按顺序连接白色执行引脚。Create Widget 的 Class 选择 WBP_UIExample，Owning Player 连接 fixture 的 Get Player。把 Return Value 保存到 Menu 和继承的 RootWidget。看不到后者时，启用 Show Inherited Variables。

OpenScreen
  Create Widget (Class = WBP_UIExample, Owning Player = GetPlayer)
  -> Set Menu = Return Value
  -> Set RootWidget = Menu
  -> Add to Viewport (Target = Menu)
  -> GetRegistry -> Register Widget
       Locator: ScreenId = demo_menu, TestId = title, Context = ""
       Widget: Menu.TitleLabel
  -> GetRegistry -> Register Widget
       Locator: ScreenId = demo_menu, TestId = continue, Context = ""
       Widget: Menu.ContinueButton
  -> Return Menu

每个 Register Widget 的 Target 连接 Get Registry。Locator 使用 Make Screen Doctor Locator，或拆分结构引脚，分别填写三个字段。Widget 引脚连接从 Menu 获取的真实 TitleLabel 或 ContinueButton 对象。最后把 Menu 连接到函数返回值，返回的是控件对象，不是布尔值。

IsReady：等待界面准备好

添加 IsReady 重写。用 Is Valid 和 Branch 检查 Menu：无效时返回 false；有效时返回 Menu 的 Is In Viewport。默认实现始终返回 false，不重写会导致等待超时。

CleanupCase：清理测试状态

添加 CleanupCase。在入口节点上右键选择 Add Call to Parent Function 并连接，再将 Menu 清空为 None。父类会移除 RootWidget 并重置注册表。本教程使用独立进程，保持 CaptureInputState 和 RestoreInputState 的默认实现。Compile、Save 后进入测试场景。

先使用默认的 100%。按照Matrix章节实现真实文字缩放后，再添加其他比例。

编写操作和检查步骤

在 Scenarios 选择 DA_UIFirstScenario，设置 ScenarioId = first_ui、Revision = 1，确认 Fixture Class 为 BP_UIFixture。

  1. 打开 Edit fixture / steps，在 Details 展开 Steps，通过数组的 + 添加五个元素。
  2. 按下表顺序填写。保持 Required 启用，超时必须为正数；前四步可使用 5 秒。
  3. 有目标的步骤中分别填写 Target.ScreenId 和 Target.TestId，Context 留空。AnalyzeLayout 则在 Layout > Targets 添加一个 locator。

在列表中选中步骤后可编辑对应属性。每个 StepId 必须唯一。重命名、删除或复制后，重新选择目标步骤。相同用途保持 ID 稳定；有意改变测试约定时增加 Revision。

窄窗口可用 Back to controls 离开 Details。回到第一次检查创建 suite 并运行一个用例。

使用稳定 ID 查找控件

Locator 由三个独立字段组成：

字段示例含义
ScreenIddemo_menu控件所属的界面。
TestIdtitle界面中的控件。
Context空或 item:42重复列表项的可选身份键。

打开界面时，将这些值与真实控件引用一起注册。不要把完整的 demo_menu/title 填入 TestId。翻译后的文字、坐标和子项序号都不是稳定 ID。

首次教程直接手动填写 ID。Refresh IDs 和 Assign locator to selected StepId 读取的是 PIE 中正在运行的 ScreenDoctor fixture 注册表。普通 Play 不会创建这个 fixture，也不会自动扫描所有游戏控件。

两个不同的活动控件使用相同 locator 会产生歧义，需要不同的 ID 或 Context。虚拟列表的适配器应先滚动并创建目标条目，再注册真实控件。尚未创建的条目本身不能证明界面出错。

选择分辨率、语言与文字大小

选中 suite 后打开 Matrix。可以增加自定义尺寸，包括 4K、超宽和竖屏，不存在三个分辨率的限制。

  1. 在 Viewport resolutions 输入整数 Width 和 Height，范围各为 1 到 16384，然后点击 Add resolution。Remove 删除对应行。至少保留一个有效尺寸。
  2. 在 Text scales 输入百分比，例如 125，点击 Add text scale。删除不需要的行。百分比框填写 125，底层 TextScales 存储 1.25。
  3. 通过 Edit cultures, input modes, exclusions and case limit 添加 en、de、fr 等语言及支持的输入方式。游戏必须已有译文和字体，选择语言不会自动翻译文字。
  4. 刷新计划。每个场景与所有分辨率、语言、比例和输入方式组合，再应用排除条件。一个场景和一种输入方式，两种分辨率、三种语言、两种比例会生成 12 个用例。
  5. 先运行一个用例，再选择 Save and run suite。超过 20 个选中用例时需要确认估算。Case Limit 限制计划，Exclusions 有意排除指定组合。

让文字比例真正作用于界面

Fixture 必须实现 ApplyTextScale，默认只接受 1.0。在 BP_UIFixture 中创建 float 变量 RequestedScale，默认值 1.0。重写 ApplyTextScale：若 Scale > 0 且 Scale <= 3，保存 Scale 并返回 true，否则 false。这是示例适配器的支持范围。回调发生在 OpenScreen 之前，此时 Menu 尚不存在。

在 OpenScreen 的 Set Menu 后、Add to Viewport 前，获取 Menu.TitleLabel，然后调用 Get Font。将输出连接到 Break Slate Font Info，再添加 Make Slate Font Info。把 Break 中的原有字段连接到 Make 的对应输入：Font Family（Font Object）、Typeface（Typeface Font Name）、材质、描边及其他可用设置。只有 Size 改用 Round(32 * RequestedScale)。把 Make 的结果传给 Menu.TitleLabel 的 Set Font，并连接白色执行引脚。找不到节点时，从字体引脚拖出并搜索 Slate Font Info。此示例只缩放标题；其他文字也要采用相同策略，或调用游戏自己的设置。始终从保存的基础字号计算，不要在已经放大的字号上再次相乘。

Viewport 是绘制区域，文字比例是游戏设置。Windows 显示缩放与物理显示器 DPI 是另外的参数。在 Matrix 输入 125% 不会改变 Windows DPI。

在 Runs 中阅读结果

  1. 在 Runs 顶部列表选择完成的运行。
  2. 左侧选择场景，然后选择 checkpoint 和输入方式。列表示分辨率/文字比例，行表示语言。
  3. 用 All cases、Needs review、Passed 或 More filters 筛选。未筛选的计数可能包含计划排除项，但它们不是实际执行的用例。
  4. 选中单元格，点击 Inspect case，通过 Next finding 查看 locator、Expected 和 Actual。
  5. 100% 显示真实像素，可滚动图像；Fit 恢复适应显示。Open original 打开原始文件。Geometry snapshot 是单独的测量证据，不是保证与每个截图像素对应的叠加图。
状态含义下一步
Passed必需检查已通过。也查看可选提示。
Needs review / ReviewNeeded测量到的情况需要人工判断。检查对应控件和图像。
NoBaseline没有兼容的已批准基准。查看并明确批准正确图像。
Failed场景中的断言未满足。查看步骤、Expected 和 Actual。
Error / Errored配置、执行或存储发生错误。查看原因和进程日志。
Unsupported所需能力不可用。实现适配器或选择支持的配置。
Complete执行已结束。单独查看结果，Complete 不等于 Passed。

Save and rerun case 使用当前保存的匹配场景。更改冻结的测试约定后，可能需要新计划。Export report 复制可分享的报告文件夹；请连同图像一起保留，不要只发送 HTML。

理解文字裁切与布局提示

AnalyzeLayout 检查指定的已注册目标；Targets 为空时检查所有已注册控件。它可标记裁切、重叠和过小的字体度量。请在附近添加 CaptureCheckpoint。

Desired 是文字布局所需大小，visible 是测量到的可用裁切区域。如果描述需要 84 像素高度，却只有 46，即使在 1920 x 1080 也会出现提示。更大的屏幕不会自动增大文本框。

这是待审查候选，不是逐字 OCR，也不能证明每处重叠都错误。装饰图层、滚动区域和有意省略的文字可能是正确设计。

  1. 打开精确用例和目标，核对语言、分辨率和比例。
  2. 查看原图及布局，检查换行、容器大小、锚点、内边距或更短的标签。
  3. 编译、保存并重跑相同条件以及其他受影响的组合。
  4. 若为有意设计，在场景设置添加范围明确的 suppression，包括 RuleId、locator、适用条件和清楚的 Reason。保留可追踪的解释。

自定义绘制、富文本和尚未创建的列表项可能需要项目适配器。Unsupported 不表示检查通过。

批准基准图像并再次比较

Baseline 是你明确认可为某一配置正确参考的图像。只保存截图并不等于验证视觉回归。

  1. 在截图步骤启用 Compare Baseline，编译并保存控件和 fixture，保存 scenario。回到 Matrix，点击 Preview selected cases and exclusions，选择更新后的用例并 Save and run selected case。修改约定后不要从 Runs 重跑旧冻结用例。新配置第一次比较通常是 NoBaseline。
  2. 在 Runs 检查该图像，再选择 Review baseline source。也可以打开 Baselines，点击 Refresh completed runs，选择完成的原始用例和 menu_state。
  3. 必要时点击 Review checkpoint，通过 Open original 或 Comparison report 全尺寸查看 Current，并核对来源、语言、分辨率与比例。
  4. 输入审查者姓名，检查阈值，只有确认正确后才点击 Approve reviewed image。来源改变后必须重新审查。
  5. 再次运行相同用例。有差异时查看 Current、Baseline 和 Diff。

运行不会自动批准。不同语言、分辨率、比例、输入与兼容渲染配置需要各自匹配的参考。更换引擎版本、scenario Revision 或字体/渲染配置可能需要重新审查。

阈值与动画区域

默认 Channel tolerance 为 8，Allowed changed fraction 为 0.0005，即未遮罩像素的 0.05%。不要为了隐藏问题而提高阈值。Advanced source and masks 可指定 JSON，排除有意变化的区域：

{"schemaVersion":1,"masks":[{"name":"clock","reason":"Animated clock","x":30,"y":20,"width":160,"height":40}]}

坐标单位是截图像素。每个遮罩必须有名称和原因，不能遮住整张图。请把批准的参考图像与项目的已审查资源一起保存。

键盘、手柄与模态窗口

第一个示例是静态界面。交互测试要求真实按钮可获得焦点，并实现正常导航和 OnClicked 行为。打开界面时设置玩家输入模式和初始焦点。

操作用途
FocusWidget设置起始焦点，单独使用不能证明导航正确。
SendKey向测试拥有焦点的界面发送 Down、Enter 或 Escape。
SendGamepadButton发送 Gamepad_DPad_Down 或 Gamepad_FaceButton_Bottom。
ClickWidget通过支持的输入路径点击已注册控件。
AssertFocused确认实际获得焦点的控件。
AssertNoModal查询 fixture 显式实现的模态观察器。

为按钮配置明确的 Down/Up 导航，发送按键，再断言焦点。不要从 fixture 直接调用 OnClicked 来代替输入测试。SendKey 和 SendGamepadButton 使用当前焦点，不使用 Target。

模态检查需要 SupportsModalObservation = true，以及返回真实打开状态的 HasOpenModal。该布尔值必须由正常打开/关闭流程更新。OnlyInputModes 可分离 Keyboard 和 Gamepad 步骤。

PIE 指 Play In Editor。同进程检查要求游戏实现完整的 CaptureInputState/RestoreInputState；没有适配器时使用独立进程，不要猜测输入恢复策略。软件手柄路径不要求物理手柄，硬件行为需另外检查。

自动运行与保存报告

可通过 Unreal 内置的 ScreenDoctor commandlet 直接执行已保存的 suite，也可用于构建任务。打开 PowerShell 终端，将项目和编辑器路径替换为自己的路径。请使用与项目相同的引擎版本。无需额外的脚本文件。

$project = 'D:\Games\MyGame\MyGame.uproject'
$editor = 'D:\Epic\UE_5.8\Engine\Binaries\Win64\UnrealEditor-Cmd.exe'
& $editor $project -run=ScreenDoctor -Action=Run -Suite='/Game/UITests/DA_UIFirstSuite.DA_UIFirstSuite' -Mode=EditorStandalone -NullRHI -unattended

/Game/UITests/DA_UIFirstSuite.DA_UIFirstSuite 是 suite 资源的对象路径，不是 Windows 文件路径。重命名资源后请同步修改。执行前请保存 suite、scenario、控件和 fixture。

退出码含义
0选中的必需检查全部通过，可能仍有预先声明的可选或已抑制提示。
1至少一项断言失败，且没有优先级更高的错误。
2配置、执行或存储错误，包括空计划。
3必需审查未解决、基准缺失、不支持/跳过、取消或执行未完成。

HTML 供阅读，JSON 保存完整详情，JUnit 用于构建工具。历史通常位于 <Project>/Saved/ScreenDoctor，基准位于 <Project>/ScreenDoctor/Baselines。请保留整个报告包。

Cancel owned queue 会停止插件自己的队列并保留已有结果。清理历史时，在下方 History 命令中指定报告目录。命令默认只预览符合条件的目录。检查预览后才添加 -Apply。-KeepLast=20 保留最近20次已完成运行和20个已完成队列。已批准基准和未完成运行受到保护。请将基准与普通历史分开保存。

& $editor $project -run=ScreenDoctor -Action=History -OutputRoot='D:\Games\MyGame\Saved\ScreenDoctor' -KeepLast=20 -NullRHI -unattended

示例中的 -NullRHI 只用于协调 commandlet。Run 会启动独立的 GPU 渲染进程来截图，这些进程需要正常工作的图形会话。若在实际游戏截图进程中使用 NullRHI，将无法生成界面图像。检查和报告在本地完成，无需在线分析服务。

检查 Development 打包游戏

打包游戏在编辑器外运行。需要 ScreenDoctor 测试执行器时使用 Development；Shipping 和 Test 不包含该模块。

  1. 在 Edit > Project Settings > Packaging 中选择需要的地图与语言。
  2. 如果没有其他资源引用，把 fixture、widget、scenario 和 suite 所在文件夹加入 Additional Asset Directories to Cook。本例是 /Game/UITests。Cook 为打包游戏准备资源，仅在编辑器可见不代表会自动加入包。
  3. 使用当前 Unreal 安装要求的编译工具生成 Win64 Development。
  4. 在 Matrix 启用 Use packaged Development executable，点击 Browse... 并选择真正的 Development .exe。
  5. 先预览并运行一个用例，确认 viewport、语言和结果文件后再运行 suite。

需要的译文和字体也必须包含在包中。本指南适用于 UE 5.5-5.8；运行和批准基准时保持插件与引擎版本一致。

常见问题

能检查超过三个分辨率吗？

可以。在 Matrix 添加和删除自己的尺寸。示例中的三列不是插件限制。

125% 会改变 Windows 缩放吗？

不会，它请求游戏或 fixture 已实现的文字比例。物理显示器 DPI 是另一回事。

安装后会自动连接所有菜单吗？

不会。通过 fixture、稳定 ID 和场景步骤连接每个界面或同类界面。先从小控件开始。

Needs review 一定是错误吗？

不一定。查看图像和测量，有意截断或装饰重叠可能符合设计。

重复运行会自动批准图片吗？

不会，必须单独审查并点击 Approve reviewed image。

插件包含奇幻界面和教程资源吗？

奇幻界面属于独立说明项目。小型 UMG 示例由你按照本指南创建，安装插件本身不会生成这些游戏资源。

需要云端分析账号吗？

不需要。ScreenDoctor 通过 Unreal 在本地检查并生成报告。
