ScreenDoctor 1.0.0 ist ein UI-Testplugin für Unreal Engine 5.5-5.8, Windows 64-bit und UMG. UMG erstellt Menüs, Schaltflächen und andere Spieloberflächen.

Neu in Unreal? Folgen Sie dem kleinen Beispiel. Eine Fixture ist ein Blueprint-Adapter zum Öffnen des Bildschirms. Ein Scenario beschreibt Prüfungen. Eine Suite verbindet Szenarien mit den auszuführenden Konfigurationen.

Das Plugin führt beschriebene Abläufe aus. Es erkundet nicht selbst alle Menüs und repariert die UI nicht automatisch. Erklärungen sind übersetzt; englische Schaltflächen- und Blueprint-Namen bleiben zum Wiederfinden erhalten.

Plugin installieren und öffnen

Passende Engine wählen

Verwenden Sie das ScreenDoctor-Paket für Ihre Unreal-Version: 5.5, 5.6, 5.7 oder 5.8. Im Epic Games Launcher steht die Version unter der Installation in Unreal Engine > Library.

Über Fab installieren

  1. Schließen Sie Unreal Editor. Suchen Sie ScreenDoctor in Ihrer Fab-Bibliothek im Epic Games Launcher und installieren Sie es für die Engine des Projekts.
  2. Öffnen Sie das Projekt und Edit > Plugins. Aktivieren Sie ScreenDoctor bei Bedarf und starten Sie den Editor neu.
  3. Öffnen Sie Tools > ScreenDoctor.

Projektinstallation aus ZIP

Der Projektordner enthält die Datei .uproject. Erstellen Sie darin bei Bedarf Plugins, schließen Sie Unreal und entpacken Sie mit dieser Struktur:

MyGame/
  MyGame.uproject
  Content/
  Plugins/
    ScreenDoctor/
      ScreenDoctor.uplugin
      Resources/
      Source/

Öffnen Sie das Projekt, aktivieren Sie ScreenDoctor unter Edit > Plugins, starten Sie neu und öffnen Sie Tools > ScreenDoctor. Kompilierte Pakete enthalten außerdem Binaries. Installieren Sie nur eine Kopie, in der Engine oder im Projekt. Reine Quellpakete benötigen passende Visual-Studio-C++-Werkzeuge und das Windows SDK, auch bei Blueprint-Projekten. Ohne eigenen Build verwenden Sie das passende kompilierte Paket.

Noch kein Projekt?

Wählen Sie beim Unreal-Start Games > Blank > Blueprint, vergeben Sie einen Namen und klicken Sie auf Create. Merken Sie sich den Speicherort. Content Drawer unten im Editor oder Strg+Leertaste zeigt Assets: gespeicherte Projektelemente wie Widgets und Testszenarien.

Erste Prüfung in einem leeren Projekt

Beginnen Sie mit einem Bildschirm, einer Sprache und einer Auflösung. Für dieses Beispiel ist kein C++ nötig. Die Anleitung verwendet englische Unreal-Menü- und Knotennamen.

  1. Öffnen Sie Content Drawer > Content. Erstellen Sie über Rechtsklick und New Folder den Ordner UITests.
  2. Wählen Sie darin User Interface > Widget Blueprint und bei der Elternauswahl User Widget. Nennen Sie das Asset WBP_UIExample und öffnen Sie es.
  3. Fügen Sie im Designer ein Canvas Panel als Wurzel hinzu, falls keines vorhanden ist. Darin erstellen Sie Text, benennen es in Hierarchy TitleLabel und aktivieren Is Variable. Text genau Settings, Schriftgröße 32, Canvas-Position X=100, Y=100, Größe 600 x 100.
  4. Fügen Sie einen Button als weiteres Canvas-Kind hinzu: ContinueButton, Is Variable und Is Focusable aktiv, Position X=100, Y=250, Größe 300 x 70. Sein Text-Kind zeigt Continue. Titel und Button liegen nebeneinander in der Hierarchie, nicht ineinander.
  5. Klicken Sie auf Compile und Save.
  6. Bearbeiten Sie Widget anbinden und Szenario beschreiben und kehren Sie danach hierher zurück.
  7. Wählen Sie unter Suites Create suite und speichern Sie DA_UIFirstSuite in Content/UITests. Öffnen Sie Edit suite properties, setzen Sie SuiteId = first_ui_suite und verwenden Sie im kompakten Fenster Back to controls. Wählen Sie unter Scenarios DA_UIFirstScenario und Add scenario to suite.
  8. Fügen Sie unter Matrix mit Add resolution 1280 x 720 hinzu und entfernen Sie die anfänglichen 1280 x 800 mit Remove. Behalten Sie 100%, en und Keyboard. Sprache und Eingabe ändern Sie über Edit cultures, input modes, exclusions and case limit; bei Bedarf danach Back to controls. Packaged-Ausführung bleibt aus.
  9. Klicken Sie auf Preview selected cases and exclusions, wählen Sie den einzigen Fall und Save and run selected case. Das Widget öffnet sich im eigenen Testprozess; die normale Play-Schaltfläche ist nicht nötig.
  10. Wählen Sie in Runs das abgeschlossene Ergebnis und sein Bild. Prüfen Sie die fünf Schritte und menu_state. Dieses erste Bild wird ohne Referenzvergleich gespeichert und beweist noch keine visuelle Übereinstimmung.
Kompilieren und speichern Sie Widget und Fixture vor dem Start. Run speichert Suite und Scenario, aber nicht automatisch alle Spiel-Blueprints.

Widget über eine Fixture anbinden

Eine Fixture basiert auf ScreenDoctorFixture. Sie öffnet das UI, registriert Steuerelemente und meldet Bereitschaft. Platzieren Sie die Fixture nicht im Level und fügen Sie nicht die Fixture selbst dem Viewport hinzu.

Asset erstellen

  1. Öffnen Sie Tools > ScreenDoctor > Scenarios, wählen Sie Create scenario und speichern Sie DA_UIFirstScenario in Content/UITests. Lassen Sie es ausgewählt.
  2. Klicken Sie auf Create Blueprint fixture, speichern und öffnen Sie BP_UIFixture. Das Plugin weist es dem Szenario zu, erstellt aber nur ein leeres Blueprint.
  3. Erstellen Sie in My Blueprint die Variable Menu vom Typ WBP_UIExample Object Reference und kompilieren Sie. Wählen Sie unter Functions > Overrides OpenScreen.

OpenScreen: UI erstellen und zurückgeben

Fügen Sie Knoten per Rechtsklick hinzu und verbinden Sie die weißen Ausführungspins der Reihe nach. Create Widget erhält WBP_UIExample und Get Player als Owning Player. Speichern Sie Return Value in Menu und dem geerbten RootWidget. Aktivieren Sie nötigenfalls Show Inherited Variables.

OpenScreen
  Create Widget (Class = WBP_UIExample, Owning Player = GetPlayer)
  -> Set Menu = Return Value
  -> Set RootWidget = Menu
  -> Add to Viewport (Target = Menu)
  -> GetRegistry -> Register Widget
       Locator: ScreenId = demo_menu, TestId = title, Context = ""
       Widget: Menu.TitleLabel
  -> GetRegistry -> Register Widget
       Locator: ScreenId = demo_menu, TestId = continue, Context = ""
       Widget: Menu.ContinueButton
  -> Return Menu

Target von Register Widget wird mit Get Registry verbunden. Erstellen Sie den Locator mit Make Screen Doctor Locator oder aufgeteiltem Strukturpin; füllen Sie die drei Felder getrennt aus. Widget erhält die echte Referenz Menu.TitleLabel beziehungsweise Menu.ContinueButton. Verbinden Sie Menu mit dem Rückgabepin der Funktion: erwartet wird ein Widget-Objekt, kein boolescher Wert.

IsReady: Bereitschaft prüfen

Überschreiben Sie IsReady. Prüfen Sie Menu mit Is Valid und Branch. Bei ungültigem Menu geben Sie false zurück, sonst Is In Viewport von Menu. Ohne Override liefert die Elternfunktion false und der Test wartet bis zum Timeout.

CleanupCase: aufräumen

Überschreiben Sie CleanupCase. Wählen Sie am Eingangsknoten per Rechtsklick Add Call to Parent Function, verbinden Sie den Aufruf und setzen Sie Menu danach auf None. Die Elternfunktion entfernt RootWidget und leert die Registry. CaptureInputState und RestoreInputState bleiben für dieses Prozessbeispiel unverändert. Compile, Save und weiter zum Szenario.

Beginnen Sie mit den standardmäßigen 100%. Andere Textgrößen erfordern die reale Umsetzung aus Matrix.

Ablauf und Prüfungen beschreiben

Wählen Sie DA_UIFirstScenario unter Scenarios. Setzen Sie ScenarioId = first_ui, Revision = 1 und Fixture Class = BP_UIFixture.

  1. Öffnen Sie Edit fixture / steps. Erweitern Sie Steps in Details und legen Sie über das + des Arrays fünf Einträge an.
  2. Tragen Sie die Werte der Tabelle in dieser Reihenfolge ein. Required bleibt aktiv. Für die ersten vier Schritte verwenden Sie 5 Sekunden Timeout.
  3. Bei zielbezogenen Schritten füllen Sie Target.ScreenId und Target.TestId getrennt aus; Context bleibt leer. Für AnalyzeLayout legen Sie einen Eintrag in Layout > Targets an.

Verlassen Sie Details im kompakten Fenster mit Back to controls. Kehren Sie zur ersten Prüfung zurück, um Suite und ersten Fall auszuführen.

Widgets mit stabilen IDs finden

Ein Locator besteht aus drei separaten Feldern:

FeldBeispielBedeutung
ScreenIddemo_menuBildschirm des Steuerelements.
TestIdtitleSteuerelement in diesem Bildschirm.
Contextleer oder item:42Optionaler Schlüssel einer wiederholten Listenzeile.

Registrieren Sie diese Werte mit der tatsächlichen Widget-Referenz beim Öffnen. Tragen Sie nicht demo_menu/title als gesamten TestId ein. Übersetzte Texte, Koordinaten und Kindindizes sind keine stabilen IDs.

Geben Sie IDs im ersten Tutorial direkt ein. Refresh IDs und Assign locator to selected StepId lesen die Registry einer aktiven ScreenDoctor-Fixture in PIE. Gewöhnliches Play erstellt diese Fixture nicht und durchsucht nicht automatisch alle Spielwidgets.

Zwei aktive Widgets mit demselben Locator sind mehrdeutig; verwenden Sie andere IDs oder Context-Werte. Für virtualisierte Listen muss Ihr Adapter zunächst zum Eintrag scrollen und dessen Widget erzeugen. Ein noch nicht erzeugter Eintrag beweist keinen UI-Fehler.

Auflösungen, Sprachen und Textgrößen wählen

Öffnen Sie Matrix mit ausgewählter Suite. Sie können eigene Größen hinzufügen, auch 4K, Hochformat und Ultrawide; drei Auflösungen sind keine Grenze.

  1. Tragen Sie unter Viewport resolutions ganzzahlige Width und Height von 1 bis 16384 ein, dann Add resolution. Remove entfernt die jeweilige Zeile. Mindestens eine gültige Größe muss bleiben.
  2. Tragen Sie unter Text scales beispielsweise 125 ein und wählen Sie Add text scale. Entfernen Sie überflüssige Zeilen. Das Prozentfeld erhält 125, während TextScales intern 1.25 enthält.
  3. Unter Edit cultures, input modes, exclusions and case limit ergänzen Sie en, de, fr und passende Eingabearten. Übersetzungen und Schriften müssen bereits im Spiel vorhanden sein; eine Kulturwahl übersetzt keinen Text.
  4. Aktualisieren Sie die Vorschau. Szenarien werden mit allen Auflösungen, Kulturen, Größen und Eingaben kombiniert, anschließend werden Ausschlüsse angewendet. Ein Szenario mit einer Eingabe, zwei Auflösungen, drei Kulturen und zwei Größen ergibt 12 Fälle.
  5. Starten Sie zuerst einen Fall und danach Save and run suite. Über 20 gewählte Fälle erfordern eine Bestätigung. Case Limit begrenzt den Plan, Exclusions lassen Kombinationen bewusst aus.

Textgröße tatsächlich anwenden

Die Fixture muss ApplyTextScale implementieren; standardmäßig ist nur 1.0 möglich. Erstellen Sie in BP_UIFixture einen float RequestedScale mit Standard 1.0. Im Override prüfen Sie Scale > 0 und Scale <= 3: speichern und true zurückgeben, andernfalls false. Das ist der Bereich dieses Beispieladapters. Der Aufruf erfolgt vor OpenScreen, wenn Menu noch nicht existiert.

In OpenScreen nach Set Menu und vor Add to Viewport rufen Sie für Menu.TitleLabel zunächst Get Font auf. Verbinden Sie das Ergebnis mit Break Slate Font Info und ergänzen Sie Make Slate Font Info. Übertragen Sie die entsprechenden vorhandenen Felder von Break nach Make: Font Family (Font Object), Typeface (Typeface Font Name), Material, Kontur und alle weiteren verfügbaren Einstellungen. Nur für Size verwenden Sie Round(32 * RequestedScale) anstelle der bisherigen Größe. Verbinden Sie das Make-Ergebnis mit Set Font für Menu.TitleLabel und auch die weißen Ausführungspins. Ziehen Sie bei Bedarf vom Schrift-Pin und suchen Sie nach Slate Font Info. Das Beispiel skaliert den Titel. Wiederholen Sie dies für weitere Texte oder verwenden Sie die tatsächliche Spieleinstellung. Rechnen Sie immer mit der gespeicherten Grundgröße, nicht mit einer bereits vergrößerten.

Viewport ist die Zeichenfläche, Textskalierung eine Spieleinstellung. Windows-Skalierung und physische Monitor-DPI sind getrennt. 125% in Matrix verändert Windows-DPI nicht.

Ergebnisse in Runs lesen

  1. Wählen Sie unter Runs oben einen abgeschlossenen Lauf.
  2. Wählen Sie links Szenario, Checkpoint und Eingabe. Spalten zeigen Auflösung/Textgröße, Zeilen Kulturen.
  3. Filtern Sie mit All cases, Needs review, Passed oder More filters. Ungefilterte Zähler können ausgeschlossene Planfälle enthalten; diese wurden nicht ausgeführt.
  4. Wählen Sie eine Zelle und Inspect case. Next finding zeigt einzelne Prüfungen mit Locator, Expected und Actual.
  5. 100% zeigt echte Pixel; scrollen Sie im Bild und kehren Sie mit Fit zurück. Open original öffnet die Datei. Geometry snapshot ist eine getrennte Messung, keine garantierte Pixelüberlagerung.

Save and rerun case verwendet das passende gespeicherte Szenario. Ein geänderter eingefrorener Testvertrag kann einen neuen Plan verlangen. Export report kopiert ein teilbares Paket. Geben Sie den gesamten Ordner einschließlich Bilder weiter, nicht nur HTML.

Abgeschnittenen Text und Layoutbefunde verstehen

AnalyzeLayout untersucht ausgewählte registrierte Ziele, bei leerer Targets-Liste alle registrierten Widgets. Mögliche Befunde betreffen Abschneiden, Überlappung und kleine Schriftmetriken. Fügen Sie nahe der Analyse einen CaptureCheckpoint hinzu.

Desired bezeichnet den Platzbedarf des Textlayouts; visible den verfügbaren gemessenen Ausschnitt. Benötigt eine Beschreibung 84 Pixel Höhe, bekommt aber nur 46, kann auch 1920 x 1080 einen Befund ergeben. Ein großer Bildschirm vergrößert nicht automatisch das Textfeld.

Dies sind Prüfkandidaten, kein OCR-Lesen jedes Zeichens. Dekorative Ebenen, Scrollbereiche und beabsichtigte Kürzungen können richtig sein.

  1. Genauen Fall öffnen und Kultur, Auflösung, Textgröße und Ziel prüfen.
  2. Original und Layout untersuchen: Umbruch, Containergröße, Anker, Innenabstand oder kürzerer Text.
  3. Änderung kompilieren, speichern und gleiche sowie betroffene andere Konfigurationen wiederholen.
  4. Beabsichtigte Ausnahmen im Szenario eng mit RuleId, Locator, passenden Dimensionen und aussagekräftigem Reason unterdrücken. Die Begründung muss nachvollziehbar bleiben.

Eigene Zeichenverfahren, Rich Text und nicht erzeugte Listeneinträge können explizite Adapter benötigen. Unsupported ist kein bestandener Test.

Referenzbild freigeben und erneut vergleichen

Eine Baseline ist ein bewusst freigegebenes korrektes Bild einer Konfiguration. Eine Aufnahme ohne Vergleich ist noch keine visuelle Regressionsprüfung.

  1. Aktivieren Sie Compare Baseline am Aufnahmeschritt. Compile/Save für UI und Fixture, Szenario speichern. Wechseln Sie zu Matrix, Preview selected cases and exclusions, wählen Sie den aktualisierten Fall und Save and run selected case. Verwenden Sie nach Vertragsänderung nicht den alten Runs-Fall. Der erste Vergleich liefert normalerweise NoBaseline.
  2. Prüfen Sie genau dieses Bild in Runs und wählen Sie Review baseline source. Alternativ unter Baselines mit Refresh completed runs den ursprünglichen abgeschlossenen Fall und menu_state wählen.
  3. Bei Bedarf Review checkpoint, dann Current über Open original oder Comparison report vollständig prüfen. Identität, Sprache, Auflösung und Größe vergleichen.
  4. Prüfernamen eingeben, Schwellen prüfen und nur ein korrektes Bild mit Approve reviewed image freigeben. Nach Quelländerung erneut prüfen.
  5. Denselben Fall wiederholen. Bei Unterschieden Current, Baseline und Diff lesen.

Ein Testlauf erteilt keine Freigabe. Jede Kultur, Auflösung, Größe, Eingabe und jeder kompatible Renderprofil-Schlüssel benötigt die passende Referenz. Engine-Version, Revision oder Schrift-/Renderprofiländerungen können eine neue Prüfung erfordern.

Schwellen und bewegte Regionen

Channel tolerance ist standardmäßig 8, Allowed changed fraction 0.0005, also 0.05% der nicht maskierten Pixel. Erhöhen Sie dies nicht zum Verbergen eines Defekts. Advanced source and masks erlaubt eine JSON-Maske für bewusst wechselnde Bereiche:

{"schemaVersion":1,"masks":[{"name":"clock","reason":"Animated clock","x":30,"y":20,"width":160,"height":40}]}

Koordinaten sind Bildpixel. Jede Maske braucht Name und Grund; vollständiges Abdecken ist unzulässig. Verwalten Sie Referenzbilder mit den geprüften Projektdateien.

Tastatur, Gamepad und modale Fenster

Das erste Beispiel ist statisch. Für Interaktion benötigen echte Buttons Fokusfähigkeit, Navigation und ihre normalen OnClicked-Aktionen. Legen Sie beim Öffnen Eingabemodus und Anfangsfokus fest.

OperationVerwendung
FocusWidgetAusgangsfokus setzen, beweist allein keine Navigation.
SendKeyDown, Enter oder Escape an die kontrollierte fokussierte UI senden.
SendGamepadButtonGamepad_DPad_Down oder Gamepad_FaceButton_Bottom senden.
ClickWidgetRegistriertes Steuerelement über den unterstützten Eingabeweg anklicken.
AssertFocusedTatsächlichen Fokus prüfen.
AssertNoModalExpliziten Modalbeobachter der Fixture verwenden.

Definieren Sie feste Down/Up-Verbindungen, senden Sie eine Taste und prüfen Sie danach den Fokus. Ein direktes OnClicked aus der Fixture ist kein Navigationstest. SendKey und SendGamepadButton verwenden den Fokus, nicht Target.

Implementieren Sie SupportsModalObservation = true und HasOpenModal mit dem tatsächlichen, beim Öffnen/Schließen aktualisierten Zustand. OnlyInputModes trennt Keyboard- und Gamepad-Schritte.

PIE bedeutet Play In Editor. Im selben Prozess brauchen Sie vollständige spielseitige CaptureInputState/RestoreInputState-Adapter. Ohne diese verwenden Sie einen getrennten Prozess. Software-Gamepad-Eingabe benötigt keinen physischen Controller; Hardwareverhalten ist ein eigener Prüfbereich.

Automatisierung und Berichte

Gespeicherte Assets lassen sich über PowerShell etwa in einem Buildjob starten. Öffnen Sie ein Terminal im Projektordner und ersetzen Sie die Beispielpfade. Bei Engine-Installation verwenden Sie deren Plugin-Scripts-Ordner.

$project = 'D:\Games\MyGame\MyGame.uproject'
$engine = 'D:\Epic\UE_5.8'
.\Plugins\ScreenDoctor\Scripts\Run-ScreenDoctorSuite.ps1   -ProjectFile $project -EngineRoot $engine   -SuiteAsset '/Game/UITests/DA_UIFirstSuite.DA_UIFirstSuite'   -Mode EditorStandalone

/Game/UITests/DA_UIFirstSuite.DA_UIFirstSuite ist ein Asset-Objektpfad, kein Windows-Dateipfad. Passen Sie ihn an umbenannte Assets an. Die Skripte liegen unter Scripts im Plugin.

ExitcodeBedeutung
0Alle ausgewählten Pflichtprüfungen bestanden; deklarierte optionale oder unterdrückte Befunde können bleiben.
1Mindestens eine Assertion fehlgeschlagen, ohne höher priorisierten Fehler.
2Konfigurations-, Ausführungs- oder Speicherfehler, auch leerer Plan.
3Offene Pflichtprüfung, fehlende Baseline, Unsupported/Skipped, Abbruch oder unvollständiger Lauf.

HTML dient zum Lesen, JSON enthält Details, JUnit für Buildsysteme. Normale Historie liegt in <Project>/Saved/ScreenDoctor, Referenzen in <Project>/ScreenDoctor/Baselines. Behalten Sie vollständige Berichtspakete.

Cancel owned queue stoppt die eigene Warteschlange und erhält verfügbare Teilergebnisse. Clear-ScreenDoctorHistory.ps1 zeigt die bereinigbaren Ordner zuerst an und löscht erst mit -Apply. Referenzen nicht wie gewöhnliche Laufhistorie löschen.

Aufnahmen brauchen eine reale GPU-Renderumgebung; NullRHI erzeugt kein UI-Bild. Die Prüfungen und Berichte bleiben lokal und benötigen keinen Onlinedienst.

Ein Development-Spielpaket prüfen

Ein Paket läuft außerhalb des Editors. Verwenden Sie Development, wenn der ScreenDoctor-Runner benötigt wird. Shipping und Test schließen ihn aus.

  1. Wählen Sie in Edit > Project Settings > Packaging die benötigten Maps und Kulturen.
  2. Nehmen Sie den Ordner mit Fixture, Widget, Szenario und Suite in Additional Asset Directories to Cook auf, falls keine anderen Referenzen ihn einschließen. Hier ist das /Game/UITests. Cook bereitet Inhalte für das Spiel vor; Editorverfügbarkeit allein reicht nicht.
  3. Erstellen Sie Win64 Development mit den Werkzeugen Ihrer Unreal-Installation.
  4. Aktivieren Sie in Matrix Use packaged Development executable und wählen Sie mit Browse... die echte Development-.exe.
  5. Plan ansehen, einen Fall ausführen und Viewport, Kultur sowie Artefakte prüfen, dann die Suite starten.

Fehlende Übersetzungen und Schriften müssen im Paket enthalten sein. Die Anleitung gilt für UE 5.5-5.8; halten Sie Plugin und Engine für Lauf und Referenzprüfung passend.

Häufige Fragen

Sind mehr als drei Auflösungen möglich?

Ja. Eigene Größen in Matrix hinzufügen und entfernen. Drei Beispielspalten sind keine Grenze.

Ändert 125% die Windows-Skalierung?

Nein. Es fordert die von Spiel oder Fixture implementierte Textgröße an. Monitor-DPI ist getrennt.

Werden nach Installation alle Spielmenüs erfasst?

Nein. Binden Sie Bildschirme oder Bildschirmgruppen mit Fixture, stabilen IDs und Szenarioschritten an.

Ist Needs review bereits ein bewiesener Fehler?

Nein. Prüfen Sie Bild und Messwerte; gewollte Kürzungen oder dekorative Überlappungen können korrekt sein.

Gibt erneutes Ausführen das Bild frei?

Nein. Freigabe benötigt getrennte Sichtprüfung und Approve reviewed image.

Sind Fantasy-UI und Tutorial-Assets im Plugin enthalten?

Die Fantasy-UI gehört zu einem getrennten Illustrationsprojekt. Das kleine UMG-Beispiel erstellen Sie anhand dieser Anleitung; Installation erzeugt diese Spielassets nicht.

Brauche ich ein Cloudkonto?

Nein. ScreenDoctor führt Tests mit Unreal aus und erstellt lokale Berichte.
