プレイヤーが不具合を見つける前に、ゲームの UI を確認しましょう。

同じ画面を異なる解像度、文字サイズ、言語で開きます。画像を比較し、切れたラベルを調べ、レイアウトを変更したら再確認できます。

最初の確認を始めるScreenDoctor をインストール
1 画面を接続2 確認内容を定義3 条件を選択4 結果を確認

ScreenDoctor 1.0.0 は Unreal Engine 5.5-5.8、Windows 64-bit、UMG 向けの UI テストプラグインです。UMG はメニューやボタンなどのゲーム画面を作る Unreal の仕組みです。

Unreal が初めてでも大丈夫です。 このガイドの小さな例から進めてください。Fixture はテスト用に画面を開く Blueprint アダプター、scenario は確認手順、suite はシナリオと実行条件をまとめたものです。

プラグインは指定した操作経路を実行します。すべてのメニューを自動探索したり、UI を自動修正したりはしません。説明は翻訳していますが、ボタン名と Blueprint ノード名は画面で見つけやすいよう英語表記を残しています。

プラグインのインストールと起動

エンジンのバージョンを合わせる

Unreal Engine 5.5、5.6、5.7、5.8 のうち、プロジェクトに対応する ScreenDoctor パッケージを使用します。Epic Games Launcher の Unreal Engine > Library でインストール済みエンジンの番号を確認できます。

Fab からインストール

  1. Unreal Editor を閉じます。ランチャーの Fab ライブラリで ScreenDoctor を探し、プロジェクトのエンジンにインストールします。
  2. プロジェクトを開き、Edit > Plugins で ScreenDoctor を検索します。必要なら有効化し、エディターを再起動します。
  3. Tools > ScreenDoctor を開きます。

ZIP をプロジェクトに配置

.uproject ファイルがあるフォルダーがプロジェクトのフォルダーです。必要なら Plugins を作成し、Unreal を閉じて次の構造で展開します。

MyGame/
  MyGame.uproject
  Content/
  Plugins/
    ScreenDoctor/
      ScreenDoctor.uplugin
      Resources/
      Source/

展開後はプロジェクトを開き、Edit > Plugins で有効化、再起動、Tools > ScreenDoctor の順に進みます。コンパイル済みパッケージには Binaries もあります。エンジン側とプロジェクト側に重複して入れず、1か所にインストールしてください。ソースのみのパッケージには適合する Visual Studio C++ ツールと Windows SDK が必要です。Blueprint のみのプロジェクトでも同じです。ビルドしたくない場合は対応するコンパイル済みパッケージを使います。

プロジェクトがまだない場合

Unreal を起動し、Games > Blank > Blueprint を選び、名前を付けて Create を押します。保存先を覚えておきましょう。画面下の Content Drawer または Ctrl+Space でアセットを管理できます。アセットとはウィジェットやシナリオなど、保存されたプロジェクトの要素です。

空のプロジェクトから最初の確認

画面、言語、解像度をそれぞれ1つにして始めます。この例の作成に C++ は不要です。以下は Unreal の英語メニューとノード名を使用します。

  1. Content Drawer > Content の空白を右クリックし、New Folder で UITests フォルダーを作ります。
  2. その中で User Interface > Widget Blueprint を選び、親クラスを聞かれたら User Widget を選択します。WBP_UIExample と名付け、開きます。
  3. Designer にルートパネルがなければ Canvas Panel を追加します。その中に Text を置き、Hierarchy で TitleLabel と名付け、Details の Is Variable を有効にします。文字は正確に Settings、フォントサイズは32、Canvas 位置は X=100, Y=100、サイズは 600 x 100 にします。
  4. Canvas に Button を追加し、ContinueButton と名付け、Is Variable と Is Focusable を有効にします。位置は X=100, Y=250、サイズは 300 x 70。ボタンの子 Text に Continue を入れます。タイトルとボタンは Canvas の別々の子にし、互いの子にしないでください。
  5. Compile と Save を押します。
  6. 下のウィジェットの接続とシナリオの定義を完了し、ここに戻ります。
  7. Suites で Create suite を選び、Content/UITests に DA_UIFirstSuite を保存します。Edit suite properties で SuiteId = first_ui_suite を設定し、狭い画面では Back to controls で戻ります。Scenarios で DA_UIFirstScenario を選び、Add scenario to suite を押します。
  8. Matrix の Add resolution で 1280 x 720 を追加し、初期値1280 x 800があれば Remove で削除します。100%、en、Keyboard だけを残します。言語と入力は Edit cultures, input modes, exclusions and case limit で変更し、必要なら操作画面へ戻ります。packaged 実行はまだ有効にしません。
  9. Preview selected cases and exclusions を押し、1つのケースを選び、Save and run selected case を押します。別のテストプロセスで画面が開きます。通常の Play は不要です。
  10. Runs で完了した結果と画像を選びます。5つの手順と menu_state を確認します。初回は基準比較をせずに画像を保存するため、まだ視覚的一致を証明するものではありません。
実行前にウィジェットと fixture をコンパイルして保存してください。Run が保存するのは suite と scenario で、ゲーム内の全 Blueprint を自動コンパイルするわけではありません。

fixture でウィジェットを接続する

Fixture は ScreenDoctorFixture を継承する Blueprint です。画面の作成、コントロールの登録、準備完了の通知を担当します。レベルに配置したり、fixture 自体をウィジェットとして viewport に追加したりしないでください。

アセットを作る

  1. Tools > ScreenDoctor > Scenarios で Create scenario を押し、Content/UITests に DA_UIFirstScenario を保存して選択したままにします。
  2. Create Blueprint fixture で BP_UIFixture を保存し、開きます。シナリオへの割り当ては行われますが、作られるのは空の Blueprint です。
  3. My Blueprint で Menu 変数を作り、型を WBP_UIExample Object Reference にして Compile します。Functions の Overrides から OpenScreen を選びます。

OpenScreen：画面を作って返す

グラフの右クリックでノードを追加し、白い実行ピンを順番に接続します。Create Widget のクラスは WBP_UIExample、Owning Player は fixture の Get Player です。Return Value を Menu と継承した RootWidget に保存します。見つからない場合は Show Inherited Variables を有効にします。

OpenScreen
  Create Widget (Class = WBP_UIExample, Owning Player = GetPlayer)
  -> Set Menu = Return Value
  -> Set RootWidget = Menu
  -> Add to Viewport (Target = Menu)
  -> GetRegistry -> Register Widget
       Locator: ScreenId = demo_menu, TestId = title, Context = ""
       Widget: Menu.TitleLabel
  -> GetRegistry -> Register Widget
       Locator: ScreenId = demo_menu, TestId = continue, Context = ""
       Widget: Menu.ContinueButton
  -> Return Menu

Register Widget の Target は Get Registry に接続します。Locator は Make Screen Doctor Locator、または構造体ピンの分割で3つの項目を別々に入力します。Widget には Menu から取得した実際の TitleLabel または ContinueButton を接続します。最後に Menu を関数の戻り値へ接続してください。返すのは boolean ではなくウィジェットです。

IsReady：準備完了を待つ

IsReady をオーバーライドし、Is Valid と Branch で Menu を確認します。無効なら false、有効なら Menu の Is In Viewport を返します。既定実装は false のため、未実装では待機がタイムアウトします。

CleanupCase：テスト状態を片付ける

CleanupCase を追加し、入口ノードを右クリックして Add Call to Parent Function を接続した後、Menu を None にします。親が RootWidget を除去し、登録をリセットします。この別プロセスの例では CaptureInputState と RestoreInputState を既定のままにします。Compile、Save の後、シナリオへ進みます。

まず100%で進めます。ほかの文字サイズはMatrixの実際の拡大処理を実装してから追加してください。

操作と確認手順を定義する

Scenarios で DA_UIFirstScenario を選び、ScenarioId = first_ui、Revision = 1、Fixture Class = BP_UIFixture を設定します。

  1. Edit fixture / steps を開き、Details の Steps 配列を展開し、+ で5要素を追加します。
  2. 下表の順に設定します。Required を有効にし、正のタイムアウトを使います。最初の4手順は5秒で構いません。
  3. 対象がある手順では Target.ScreenId と Target.TestId を別々に入力し、Context は空欄にします。AnalyzeLayout では Layout > Targets に1要素を追加します。

ExpectedText はウィジェットの Settings と完全一致させます。キャプチャの Compare Baseline はオフにし、後で基準画像を承認するときに有効化します。

一覧から手順を選ぶと編集できます。StepId は重複できません。名前変更、削除、複製後は目的の手順を選び直します。同じ目的の ID は維持し、テストの約束を意図的に変えるときは Revision を増やします。

狭い画面では Back to controls で Details を閉じます。最初の確認に戻り、suite を作成して1ケース実行します。

安定した ID でウィジェットを探す

Locator は次の3つの別々の項目で構成します。

項目例意味
ScreenIddemo_menuコントロールが属する画面。
TestIdtitleその画面内のコントロール。
Context空欄または item:42繰り返し項目の任意の識別キー。

画面を開くとき、実際のウィジェット参照と一緒に登録します。demo_menu/title 全体を TestId に入れないでください。翻訳された表示文字、座標、子の順番は安定した ID ではありません。

最初は ID を直接入力します。Refresh IDs と Assign locator to selected StepId は PIE で動作中の ScreenDoctor fixture の登録を読みます。通常の Play は fixture を作らず、ゲーム全体のウィジェットも自動探索しません。

異なる生存中のウィジェットに同じ locator を付けると曖昧になります。ID または Context を分けてください。仮想化リストでは、アダプターでスクロールして項目を実体化してから登録します。まだ生成されていない項目だけで UI の不具合とは判断できません。

解像度、言語、文字サイズを選ぶ

Suite を選び Matrix を開きます。4K、横長、縦長など任意のサイズを追加できます。3つまでという制限はありません。

  1. Viewport resolutions に整数の Width と Height を入力し、Add resolution を押します。各辺は1から16384です。Remove で行を削除し、最低1サイズは残します。
  2. Text scales に 125 などのパーセントを入れ、Add text scale を押します。不要な行は削除できます。パーセント欄は125、内部の TextScales は1.25です。
  3. Edit cultures, input modes, exclusions and case limit で en、de、fr などの言語と、画面が対応する入力方式を追加します。翻訳とフォントはゲーム側に必要です。文化コードを選んでも自動翻訳はされません。
  4. プランを更新します。各シナリオとすべての解像度、言語、倍率、入力を組み合わせ、除外を適用します。1シナリオ、1入力、2解像度、3言語、2倍率なら12ケースです。
  5. 先に1ケース、その後 Save and run suite を実行します。選択が20ケースを超える場合は見積もりの確認が必要です。Case Limit はプランの上限、Exclusions は意図的な除外です。

実際の文字に倍率を適用する

Fixture で ApplyTextScale を実装します。既定は1.0のみです。BP_UIFixture に float の RequestedScale を作り初期値1.0にします。Override では Scale > 0 かつ Scale <= 3 なら保存して true、それ以外は false を返します。この範囲は例のアダプターの設定です。呼び出しは OpenScreen より前なので Menu はまだありません。

OpenScreen の Set Menu の後、Add to Viewport の前に Menu.TitleLabel から Get Font を取得します。出力を Break Slate Font Info につなぎ、Make Slate Font Info を追加します。Break の既存フィールドを Make の対応する入力につなぎます。Font Family（Font Object）、Typeface（Typeface Font Name）、マテリアル、アウトライン、その他の公開設定を引き継ぎます。Size だけを Round(32 * RequestedScale) に変更します。Make の出力を Menu.TitleLabel の Set Font に渡し、白い実行ピンも接続します。見つからない場合はフォントのピンからドラッグし、Slate Font Info を検索します。この例は見出しだけを拡大するため、他のテキストにも同じ方針を適用するか、ゲームの実際の設定を呼び出してください。拡大済みのサイズではなく、保存した基本サイズから計算します。

Viewport は描画領域、文字倍率はゲーム内設定です。Windows の表示倍率や物理モニターの DPI とは別物です。Matrix に125%を入れても Windows の DPI は変わりません。

Runs で結果を読む

  1. Runs 上部の一覧から終了した実行を選びます。
  2. 左でシナリオ、次に checkpoint と入力方式を選びます。列は解像度と文字倍率、行は言語です。
  3. All cases、Needs review、Passed、More filters で絞り込みます。未絞り込みの合計に除外予定ケースが含まれることがありますが、それらは実行済みではありません。
  4. セルを選び Inspect case を押します。Next finding で locator、Expected、Actual を読みます。
  5. 100% で実ピクセル表示し、スクロールして確認します。Fit で全体表示、Open original でファイルを開けます。Geometry snapshot は別の測定で、全ピクセルと対応する保証のある重ね合わせではありません。
状態意味対応
Passed必須の確認に合格。任意の指摘も読みます。
Needs review / ReviewNeeded測定された状態の確認が必要。該当ウィジェットと画像を調べます。
NoBaseline互換性のある承認済み基準がありません。正しい画像を確認して承認します。
Failed指定した条件が成立しませんでした。手順、Expected、Actual を読みます。
Error / Errored設定、実行、保存のエラー。理由とプロセスログを確認します。
Unsupported要求した機能がありません。アダプターを実装するか条件を変更します。
Complete実行が終了した状態。結果は別に確認します。Passed とは限りません。

Save and rerun case は対応する保存済みシナリオを使います。固定されたテスト条件の変更後は新しいプランが必要になる場合があります。Export report は共有用フォルダーをコピーします。HTML だけでなく画像も含めて渡してください。

文字切れとレイアウトの指摘を理解する

AnalyzeLayout は指定した登録済み対象、Targets が空ならすべての登録済みウィジェットを調べます。切れ、重なり、小さなフォントメトリックを指摘できます。近くに CaptureCheckpoint を追加してください。

Desired は文字レイアウトの要求サイズ、visible は測定した利用可能なクリップ領域です。高さ84ピクセルが必要な説明に46しかない場合、1920 x 1080でも指摘されます。画面を大きくしても小さなテキスト枠は自動で広がりません。

これは確認候補であり、全グリフの OCR や、すべての重なりが誤りという判定ではありません。装飾、スクロール領域、意図的な省略を確認しましょう。

  1. 正確なケースと対象を開き、言語、解像度、倍率を確認します。
  2. 元画像とレイアウトで、折り返し、領域サイズ、アンカー、余白、短いラベルを検討します。
  3. Compile、Save 後に同じ条件と影響するほかの構成を再実行します。
  4. 意図した状態なら、シナリオの suppression に RuleId、locator、条件、明確な Reason を設定します。限定した抑制にして理由を残します。

独自描画、リッチテキスト、未生成のリスト項目は明示的なアダプターが必要な場合があります。Unsupported は合格ではありません。

基準画像を承認して再比較する

Baseline は、特定の条件で正しいと自分で承認した画像です。単に保存した画像は視覚的な回帰チェックではありません。

  1. キャプチャの Compare Baseline を有効にし、ウィジェットと fixture を Compile/Save、シナリオも保存します。Matrix で Preview selected cases and exclusions を更新し、新しいケースを選んで Save and run selected case を実行します。条件変更後に Runs の古い固定ケースを再実行しないでください。初回比較は通常 NoBaseline です。
  2. Runs でその画像を確認し Review baseline source を選びます。または Baselines の Refresh completed runs で元の完了ケースと menu_state を選びます。
  3. 必要なら Review checkpoint を押し、Current を Open original または Comparison report で全体確認します。識別情報、言語、解像度、倍率を照合します。
  4. 確認者名を入力し、しきい値を確認して、正しい画像だけ Approve reviewed image で承認します。元データが変わったら再確認が必要です。
  5. 同じケースを再実行します。違いがあれば Current、Baseline、Diff を調べます。

実行と承認は別です。言語、解像度、倍率、入力、互換レンダリングプロファイルごとに対応する基準が必要です。エンジン、Revision、フォントや描画設定の変更は再確認を必要とする場合があります。

しきい値と動く領域

既定の Channel tolerance は8、Allowed changed fraction は0.0005、マスク外の0.05%です。不具合を隠すために増やさないでください。Advanced source and masks から意図的に動く領域の JSON を指定できます。

{"schemaVersion":1,"masks":[{"name":"clock","reason":"Animated clock","x":30,"y":20,"width":160,"height":40}]}

座標は画像のピクセルです。各マスクに名前と理由が必要で、全体を覆うことはできません。承認済み画像は確認対象のプロジェクトファイルと一緒に管理します。

キーボード、ゲームパッド、モーダル画面

最初の例は静止画面です。操作テストでは実際のボタンをフォーカス可能にし、ナビゲーションと通常の OnClicked を実装します。画面を開くとき入力モードと初期フォーカスを設定します。

操作用途
FocusWidget開始フォーカスの設定。単独では移動の確認になりません。
SendKey所有するフォーカスへ Down、Enter、Escape を送信。
SendGamepadButtonGamepad_DPad_Down、Gamepad_FaceButton_Bottom を送信。
ClickWidget登録済み対象を対応する入力経路でクリック。
AssertFocusedフォーカスがある対象を確認。
AssertNoModalfixture の明示的なモーダル観測を確認。

ボタン間に明示的な Down/Up を設定し、キー送信後にフォーカスを確認します。fixture から直接 OnClicked を呼ぶ方法では入力を確認できません。SendKey と SendGamepadButton は現在のフォーカスを使い、Target は使いません。

モーダル確認には SupportsModalObservation = true と、実際の開閉フラグを返す HasOpenModal が必要です。通常の開閉処理でフラグを更新します。OnlyInputModes で Keyboard と Gamepad の手順を分けます。

PIE は Play In Editor です。同じプロセスではゲーム側による完全な CaptureInputState/RestoreInputState が必要です。なければ別プロセスを使います。ソフトウェアのゲームパッド経路には物理コントローラーは不要ですが、機器固有の動作は別の確認対象です。

自動実行とレポートの保存

保存した suite は Unreal 組み込みの ScreenDoctor commandlet で直接実行でき、ビルド処理にも組み込めます。PowerShell ターミナルを開き、プロジェクトとエディターのパスを自分の環境に置き換えます。プロジェクトと同じエンジンバージョンを使用してください。追加のスクリプトファイルは不要です。

$project = 'D:\Games\MyGame\MyGame.uproject'
$editor = 'D:\Epic\UE_5.8\Engine\Binaries\Win64\UnrealEditor-Cmd.exe'
& $editor $project -run=ScreenDoctor -Action=Run -Suite='/Game/UITests/DA_UIFirstSuite.DA_UIFirstSuite' -Mode=EditorStandalone -NullRHI -unattended

/Game/UITests/DA_UIFirstSuite.DA_UIFirstSuite は suite アセットのオブジェクトパスで、Windows ファイルパスではありません。改名した場合は変更します。実行前に suite、scenario、ウィジェット、fixture を保存してください。

HTML は閲覧用、JSON は詳細、JUnit はビルドツール用です。通常の履歴は <Project>/Saved/ScreenDoctor、基準は <Project>/ScreenDoctor/Baselines にあります。レポート一式を保存してください。

Cancel owned queue はプラグインのキューを停止し、利用可能な途中結果を残します。履歴を整理するには、次の History コマンドでレポートフォルダーを指定します。最初は削除候補を表示するだけです。内容を確認してから -Apply を追加してください。-KeepLast=20 は最新の完了した実行を20件、完了したキューを20件保持します。承認済み基準と未完了の実行は保護されます。基準は通常の履歴と別に保存してください。

& $editor $project -run=ScreenDoctor -Action=History -OutputRoot='D:\Games\MyGame\Saved\ScreenDoctor' -KeepLast=20 -NullRHI -unattended

この例の -NullRHI は調整用 commandlet に適用されます。Run はキャプチャ用に GPU 描画を行う別プロセスを起動するため、動作するグラフィックスセッションが必要です。ゲーム自体を NullRHI で実行しても UI 画像は生成できません。チェックとレポートはローカルで処理され、オンライン分析サービスは不要です。

Development パッケージのゲームを確認する

パッケージ済みゲームはエディター外で動きます。テスト実行モジュールが必要な場合は Development を使います。Shipping と Test には含まれません。

  1. Edit > Project Settings > Packaging で必要なマップと言語を選択します。
  2. 他から参照されない場合は fixture、widget、scenario、suite のフォルダーを Additional Asset Directories to Cook に含めます。本例は /Game/UITests。Cook はゲーム向けにアセットを準備する処理で、エディターにあるだけでは同梱されません。
  3. Unreal に必要なツールで Win64 Development をパッケージします。
  4. Matrix で Use packaged Development executable を有効にし、Browse... で実際の Development .exe を選びます。
  5. プランを確認し1ケース実行して、viewport、言語、結果ファイルを確認してから全体を実行します。

翻訳とフォントも含めてください。このガイドは UE 5.5-5.8 を対象とし、実行と基準承認では対応するプラグインとエンジンを使用します。

よくある質問

3つ以上の解像度を使えますか？

はい。Matrix で追加と削除ができます。例の3列は制限ではありません。

125% は Windows の倍率を変えますか？

いいえ。ゲームまたは fixture が実装した文字倍率を要求します。モニターの DPI とは別です。

インストールで全メニューが自動接続されますか？

いいえ。Fixture、安定した ID、手順で画面や画面群を接続します。最初は小さな例から進めます。

Needs review は確定した不具合ですか？

いいえ。画像と測定を見て判断します。省略や装飾的な重なりは意図的な場合があります。

再実行すると画像が承認されますか？

いいえ。別途確認し、Approve reviewed image を明示的に押す必要があります。

ファンタジー画面や練習アセットは同梱ですか？

ファンタジー画面は別の説明用プロジェクトです。小さな UMG 例はこの手順で自分で作り、インストールだけでは生成されません。

クラウド分析のアカウントが必要ですか？

不要です。ScreenDoctor は Unreal でローカル実行し、ローカルにレポートを作ります。
